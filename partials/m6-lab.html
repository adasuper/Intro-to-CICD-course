Lab 5: Test Pipeline on Gitee Go

Automate your pytest suite, then drive a change through the branch, PR, and master pipelines.

This lab uses the tested project from Lab 4 (src/board.py, src/tictactoe.py, and your tests/test_board.py). You'll put pytest behind automated pipelines and watch all three pipeline types from Class 11 fire.

1 · Confirm the tests pass locally

From the project root, make sure the suite is green before automating it; the pipeline can only run what already works on your machine:

pytest

If pytest isn't found, install it with pip install pytest (see Module 1). Record the test dependencies so the pipeline installs the same ones: create a requirements.txt. The pipeline writes an HTML test report, which needs the pytest-html plugin:

# requirements.txt
pytest
pytest-html

2 · Set up the three pipelines

Enable Gitee Go on your repo (the Services tab). You'll create three pipelines under .workflow/, one per trigger type from Class 11. Start with the master pipeline: create a pipeline from the Python template and replace it with the file below, the three-stage Compile → Test → Publish file (see Class 11 for a key-by-key explanation):

# .workflow/master-pipeline.yml
version: '1.0'
name: master-pipeline
displayName: MasterPipeline
triggers:
  trigger: auto
  push:
    branches:
      include:
        - master
stages:
  - name: compile
    displayName: Compile
    strategy: naturally
    trigger: auto
    steps:
      - step: build@python
        name: build_python
        displayName: Python Build
        pythonVersion: '3.13'
        commands:
          - python3 -m pip install --upgrade pip
          - pip3 config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
          - pip3 install -r requirements.txt
          - python3 -m compileall src
        artifacts:
          - name: BUILD_ARTIFACT
            path:
              - ./
      - step: publish@general_artifacts
        name: publish_general_artifacts
        displayName: Upload Artifact
        dependArtifact: BUILD_ARTIFACT
        artifactName: output
        dependsOn: build_python
  - name: test
    displayName: Test
    strategy: naturally
    trigger: auto
    executor: []
    steps:
      - step: ut@python
        name: unit_test_python
        displayName: Python Unit Tests
        pythonVersion: '3.13'
        commands:
          - pip3 config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
          - pip3 install -r requirements.txt
          - pytest --html=report/index.html
        report:
          path: report
          index: index.html
        checkpoints: []
        caches: []
        notify: []
        strategy:
          retry: '0'
  - name: release
    displayName: Publish
    strategy: naturally
    trigger: auto
    steps:
      - step: publish@release_artifacts
        name: publish_release_artifacts
        displayName: Publish
        dependArtifact: output
        version: 1.0.0.0
        autoIncrement: true
        strategy: {}

This is the real file from Gitee's Python template; the empty fields (executor, checkpoints, caches, notify, strategy) are editor defaults you can leave as-is.

Now add a branch pipeline and a PR pipeline. Both are copies of the master pipeline with the release (Publish) stage removed (you don't publish from unmerged work) and a different trigger. When you create each one in Gitee Go, pick its trigger type and Gitee writes the matching triggers block:

# branch pipeline: fires on a push to any non-master branch (Compile + Test, no Publish)
triggers:
  trigger: auto
  push:
    branches:
      exclude:
        - master
# PR pipeline: fires when a Pull Request targets master (Compile + Test, no Publish)
triggers:
  trigger: auto
  pr:
    branches:
      include:
        - master

The exact trigger keys come from the Gitee Go editor when you choose a pipeline's trigger type (master branch / regular branch / pull request); keep the shape: branch and PR pipelines run Compile + Test, never Publish.

3 · Exercise the branch pipeline: red, then green

  1. Create a dev branch off master and switch to it: git switch -c dev.
  2. Make a small change on dev that introduces a bug one of your tests catches: for example, in src/board.py change the anti-diagonal line back to (2, 4, 8), so test_anti_diagonal_win will fail. Commit and push the branch: git push -u origin dev.
  3. On Gitee, watch the branch pipeline run and turn red. Open the failed Test stage and read the failing assertion in the HTML report.
  4. Fix the bug (restore (2, 4, 6)), commit, and push again. The branch pipeline re-runs and turns green.

4 · Open a PR (PR pipeline), then merge (master pipeline)

  1. On Gitee, open a Pull Request from dev into master. The PR pipeline runs against the proposed merge; confirm it is green (a red PR pipeline blocks the merge).
  2. Merge the PR. The push to master triggers the master pipeline: Compile → Test → Publish, which publishes a versioned release.
  3. Tidy up: delete the dev branch (Gitee's button after the merge, and git branch -d dev locally).

A screenshot of all three pipelines' run history: the branch pipeline showing a red run followed by a green run, the PR pipeline's green run, and the master pipeline's green run that published the release.

Done when

All three pipelines exist and have fired: the branch pipeline went red then green, the PR pipeline gated the merge, and merging ran the master pipeline through to a published release.
