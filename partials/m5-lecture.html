Make

Why manual g++ doesn't scale, and how to describe a build once and repeat it with a single command.

As soon as a project has more than one source file, typing g++ commands by hand becomes error-prone and unrepeatable. Make lets you record your build in one file, the Makefile. You then type make, and it runs the right compiler commands for you, rebuilding only what actually changed.

1 · The simplest Makefile

Recall the hello project from the Setup Lab: a single hello.cpp you compiled by hand with g++ hello.cpp -o hello. A Makefile records that command as a rule. Create a file named Makefile (no extension) next to hello.cpp:

hello: hello.cpp
	g++ hello.cpp -o hello

That single rule has three parts:

  • Target: hello, the file we want to produce (left of the colon).
  • Prerequisites: hello.cpp, what the target is built from (right of the colon).
  • Recipe: the indented g++ … line, the shell command that builds the target.

Now just type make:

make
# g++ hello.cpp -o hello
./hello
# Hello, world!
Tabs, not spaces

Every recipe line must begin with a real Tab character, never spaces; this is Make's most infamous gotcha. If you see Makefile:2: *** missing separator. Stop., your editor turned the Tab into spaces; switch that line's indentation back to a Tab. (In VS Code, the Makefile Tools extension handles this for you.)

2 · The default goal & "up to date"

Running make with no arguments builds the first target in the file, the default goal. You can also name one explicitly: make hello. Run make a second time without changing anything:

make
# make: 'hello' is up to date.

Make compares timestamps: it rebuilds a target only when a prerequisite is newer than the target. Edit hello.cpp (or touch hello.cpp) and make recompiles; otherwise it does nothing. On one file that hardly matters; on a big project it turns a minutes-long rebuild into a seconds-long one. That is the whole point of a build system.

3 · More than one file

Real programs span several files. Let's grow hello by moving the greeting into its own unit, giving three files:

// greeter.h
#ifndef GREETER_H
#define GREETER_H
#include <string>
std::string greet(const std::string& name);
#endif
// greeter.cpp
#include "greeter.h"
std::string greet(const std::string& name) {
    return "Hello, " + name + "!";
}
// main.cpp
#include <iostream>
#include "greeter.h"
int main() {
    std::cout << greet("world") << "\n";
}

The naive Makefile compiles them all in one command:

hello: main.cpp greeter.cpp greeter.h
	g++ main.cpp greeter.cpp -o hello

It works, but it recompiles both sources whenever you touch either one. We can do better.

4 · Separate compilation & incremental builds

Building is really two steps: turn each .cpp into an object file (.o), then link the objects into one executable. Giving each step its own rule lets Make rebuild only what changed:

hello: main.o greeter.o
	g++ main.o greeter.o -o hello

main.o: main.cpp greeter.h
	g++ -c main.cpp

greeter.o: greeter.cpp greeter.h
	g++ -c greeter.cpp

g++ -c main.cpp compiles without linking, producing main.o. Make now understands a small dependency graph:

hello
├── main.o      ← main.cpp + greeter.h
└── greeter.o   ← greeter.cpp + greeter.h

Edit only greeter.cpp and run make: it rebuilds greeter.o and relinks hello, but skips main.o because main.cpp didn't change. Both objects list greeter.h as a prerequisite, so editing the header correctly rebuilds both.

5 · Variables

The compiler name and flags repeat on every line. Pull them into variables and reference them with $(…):

CXX = g++
CXXFLAGS = -std=c++17 -Wall

hello: main.o greeter.o
	$(CXX) $(CXXFLAGS) main.o greeter.o -o hello

main.o: main.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c main.cpp

greeter.o: greeter.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c greeter.cpp

Now adding a flag or switching compilers is a one-line change applied everywhere. CXX and CXXFLAGS are conventional names, but any name works. The two flags we pass are worth knowing:

  • -std=c++17: compile against the C++17 language standard. Without it, g++ may default to an older standard and reject modern syntax; pinning the version makes the build behave the same on every machine.
  • -Wall: turn on the common warnings ("all" the usual ones). Warnings flag suspicious code (an unused variable, a function that forgets to return) that still compiles but is often a bug. Treat them as a free code review.

Other flags you'll meet: -Iinclude (also written -I include) adds a folder to the compiler's header search path, so #include "board.h" is found when the header lives in an include/ subfolder; -g adds debug information; -O2 turns on optimisation.

6 · Automatic variables

The recipes still repeat file names. Make fills in three automatic variables per rule:

  • $@: the target.
  • $^: all prerequisites.
  • $<: the first prerequisite.
hello: main.o greeter.o
	$(CXX) $(CXXFLAGS) $^ -o $@

main.o: main.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $<

greeter.o: greeter.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $<

For hello, $^ expands to main.o greeter.o and $@ to hello. In the object rules we use $< (the .cpp), not $^, so the header isn't handed to the compiler as a source file.

7 · Pattern rules

The two object rules are now identical except for the names. A pattern rule using % as a wildcard collapses them into one rule that builds any .o from the matching .cpp:

%.o: %.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $< -o $@

The % matches the stem: for greeter.o it is greeter, so the prerequisite becomes greeter.cpp. One rule now covers every source file you add.

8 · Phony targets: clean and run

Not every target is a file. clean deletes build output; run builds then launches the program. Since no file named clean exists, make clean normally runs, but if someone ever created a file called clean, Make would think it was "up to date" and skip it. Declaring these targets .PHONY tells Make they are commands, not files:

.PHONY: clean run

clean:
	rm -f hello *.o

run: hello
	./hello

make run depends on hello, so Make builds the program first (if needed), then runs it.

But these two recipes are environment-specific. rm -f and ./hello are Unix conventions (macOS, Linux, and Git Bash). In a native Windows shell (PowerShell or Command Prompt) the delete command is del, and the executable is hello.exe, launched without the ./ prefix. So clean and run have to adapt: the complete Makefile below detects which shell you are running in and picks the right commands automatically.

9 · The complete Makefile

Putting every idea together, and making clean and run work in any shell, gives this complete, portable Makefile for the multi-file hello project:

CXX = g++
CXXFLAGS = -std=c++17 -Wall

# Ask the shell what it is: a POSIX shell (Linux, macOS, Git Bash) has
# `uname`; a native Windows shell (cmd / PowerShell) does not.
UNAME := $(shell uname 2>/dev/null)

ifeq ($(UNAME),)
    EXE = hello.exe
    RM  = del /Q /F
    RUN = $(EXE)
else
    EXE = hello
    RM  = rm -f
    RUN = ./$(EXE)
endif

$(EXE): main.o greeter.o
	$(CXX) $(CXXFLAGS) $^ -o $@

%.o: %.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $< -o $@

.PHONY: clean run

clean:
	-$(RM) $(EXE) *.o

run: $(EXE)
	$(RUN)

Instead of keying off the operating system, this version asks the shell what it is. The detection line repays reading token by token:

UNAME := $(shell uname 2>/dev/null)
  • UNAME: the variable we are defining (any name works; this one is conventional).
  • :=: a simply-expanded assignment: the right-hand side is evaluated once, right now, and the result is stored. With a plain = the value would be recursively expanded, re-evaluated every time UNAME is used, which would re-run the command on each reference. := runs uname exactly once.
  • $(shell …): Make's shell function: it runs the command inside a subshell and substitutes the command's standard output back into the Makefile (with the trailing newline stripped). So UNAME becomes whatever uname printed.
  • uname: the Unix command that prints the kernel/OS name: Linux, Darwin (macOS), or MINGW64_NT-… (Git Bash). A native Windows shell has no such command.
  • 2>/dev/null: shell redirection: send file descriptor 2 (standard error) to the null device, i.e. discard it. When uname is missing, Windows prints a "command not found" message to stderr; this throws that message away so it doesn't clutter the output, leaving UNAME simply empty.

So UNAME ends up as either the shell's name or an empty string, and two cases follow:

  • Empty (no uname) → Command Prompt or PowerShell: delete with del, run the bare hello.exe.
  • Anything else (a POSIX shell: Linux, Darwin, or Git Bash) → use rm and ./hello.

The rules use $(EXE), $(RM), and $(RUN) instead of hard-coded names, so one file works for everyone. The leading - in -$(RM) … tells Make to ignore errors from that line, so make clean still succeeds even when there is nothing to delete.

Works in any shell

Because the choice is driven by uname rather than the OS, the clean and run targets behave correctly whether you run make from Git Bash, PowerShell, or Command Prompt, with no need to remember which one.

make builds it, make run builds-and-runs, make clean resets. For a deeper reference, the community favourite is makefiletutorial.com.

10 · Organising files into folders

So far every file (headers, sources, the Makefile, and the compiled output) has sat in one folder. That is fine for three files, but it stops scaling the moment a project grows: headers get tangled up with implementation, and, crucially, there is nowhere clean to put tests. The conventional layout separates code by its role:

hello/
├── include/
│   └── greeter.h        # public headers (the interface)
├── src/
│   ├── greeter.cpp      # implementation (the logic)
│   └── main.cpp         # entry point / I/O
├── tests/
│   └── test_greeter.cpp # tests for the logic (added in Module 6)
├── build/               # compiled output: objects + executable (generated; gitignored)
└── Makefile
  • include/ holds the headers: the declarations other files #include.
  • src/ holds the implementation, split so the logic (greeter.cpp) is separate from the entry point / I/O (main.cpp).
  • tests/ holds test programs that exercise the logic.

Why this matters for testing. A test needs to call your logic (greet()) but must not drag in main(): a program can have only one main, and the test supplies its own. Because the logic lives in its own src/greeter.cpp, separate from src/main.cpp, a test in tests/ can compile against greeter.cpp alone, with no keyboard and no clashing main(). In Module 6 you will do exactly that. Organising the files now is what makes automated testing possible later.

Build output should be kept out of the source folders too. This Makefile writes every object file and the executable into a generated build/ folder, so src/, include/, and the project root only ever hold things you actually wrote (add build/ to .gitignore). That takes a few coordinated changes: point the compiler at the headers with -Iinclude, read sources from src/, write outputs under build/, and create that folder before compiling.

CXX = g++
CXXFLAGS = -std=c++17 -Wall -Iinclude
BUILD = build

UNAME := $(shell uname 2>/dev/null)

ifeq ($(UNAME),)
    EXE   = $(BUILD)/hello.exe
    MKDIR = if not exist $(BUILD) mkdir $(BUILD)
    RMDIR = if exist $(BUILD) rmdir /S /Q $(BUILD)
    RUN   = $(subst /,\,$(EXE))
else
    EXE   = $(BUILD)/hello
    MKDIR = mkdir -p $(BUILD)
    RMDIR = rm -rf $(BUILD)
    RUN   = ./$(EXE)
endif

$(EXE): $(BUILD)/main.o $(BUILD)/greeter.o
	$(CXX) $(CXXFLAGS) $^ -o $@

$(BUILD)/%.o: src/%.cpp include/greeter.h | $(BUILD)
	$(CXX) $(CXXFLAGS) -c $< -o $@

$(BUILD):
	$(MKDIR)

.PHONY: clean run

clean:
	$(RMDIR)

run: $(EXE)
	$(RUN)
  • BUILD = build names the output folder once, so every other line refers to it by variable.
  • -Iinclude adds the include/ folder to the compiler's header search path, so #include "greeter.h" resolves even though the header is not beside the source. The name include is only a convention: the flag is -I followed by whatever your folder is called (headers in headers/ would use -Iheaders, with the prerequisite path updated to match). You can list several folders with several -I flags.
  • The pattern rule $(BUILD)/%.o: src/%.cpp reads each source from src/ and writes its object into build/ (so build/greeter.o is built from src/greeter.cpp); include/greeter.h is a prerequisite so editing the header rebuilds the objects.
  • The $(BUILD): rule creates the output folder before anything is compiled into it. Because creating and deleting a folder is shell-specific, the same uname check also sets MKDIR (mkdir -p on Unix vs if not exist … mkdir on Windows) and RMDIR (rm -rf vs rmdir /S /Q). make clean now just removes the whole build/ folder.
  • RUN on Windows wraps the path in $(subst /,\,$(EXE)) because the cmd shell needs back-slashes (build\hello.exe) to launch a program, while g++ and Make accept forward slashes everywhere else.
