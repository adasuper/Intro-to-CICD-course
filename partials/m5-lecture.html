Testing with pytest

Write small checks that prove your code behaves, and run them all with one command.

Until now you've tested by hand: run the program, type some moves, eyeball the output. That doesn't scale: it's slow, easy to skip, and a fix in one place can silently break another. Automated tests are small programs that check your code for you, in seconds, every time. pytest is the tool that finds and runs them.

1 · Why automated tests

Manual testing has three problems: it's slow, it gets skipped when you're in a hurry, and it misses regressions: a change that quietly breaks something that used to work. An automated test pins down one expected behaviour once; from then on, every time you change the code, the test tells you in seconds whether you broke it.

  • The anti-diagonal bug from Lab 3 (cells 3-5-7 not detected) is exactly the kind of thing a single test would have caught the moment it was introduced.
  • Tests double as documentation: they show, in code, how a function is meant to be used.
  • They are a safety net for refactoring: change the insides freely, and if the tests still pass, the behaviour is intact.
  • The payoff compounds in Module 6, where the CI pipeline runs your tests automatically on every push.

2 · Make code testable: separate logic from I/O

A test calls your code and checks what comes back. It can't easily "type into" an input() prompt or read what print() put on screen. The fix is to keep the decisions and rules (pure logic) in functions that take arguments and return values, separate from the input()/print() that talk to the user.

Take the hello project. Instead of one script that prints directly, move the logic into a function that returns a string:

# greeter.py: pure logic, no I/O
def greet(name):
    return f"Hello, {name}!"

The I/O (asking for a name, printing the result) lives elsewhere. Now greet() is trivially testable: hand it a name, check the string it returns. A function that returns a value is easy to test; a function that only prints is not.

3 · Organise the project: src/ and tests/

So far everything has lived in one folder. As a project grows, that gets crowded: source files, test files, and generated junk all jumbled together. The common convention is to give each a home: application code in a src/ folder, tests in a tests/ folder.

hello/
├── src/
│   └── greeter.py       # the code under test
├── tests/
│   └── test_greeter.py  # the tests
└── pyproject.toml       # tells pytest where the code lives

There's one catch: once greeter.py moves into src/, the line from greeter import greet can no longer find it: src/ isn't on Python's import path. Rather than set PYTHONPATH by hand every time, add a small pyproject.toml at the project root and let pytest handle it:

# pyproject.toml
[tool.pytest.ini_options]
pythonpath = ["src"]

That one setting tells pytest to add src/ to the import path before it runs, so your tests keep writing from greeter import greet unchanged. The file also marks the project root, so pytest discovers the same tests/ no matter which sub-folder you launch it from.

4 · Writing and running a test

pytest discovers tests by name: files called test_*.py and functions called test_*. A test calls the function and asserts the result is what you expect:

# test_greeter.py
from greeter import greet

def test_greet_uses_the_name():
    result = greet("world")            # Act
    assert result == "Hello, world!"    # Assert

Every test follows the same three beats: Arrange a situation, Act by calling the code, Assert the result. The assert is plain Python: if its expression is false, the test fails. To run every test in the project, go to the project root (the folder with pyproject.toml) and just type:

pytest

pytest reads pyproject.toml, puts src/ on the import path, then finds and runs every test_*.py under tests/; you never name the files yourself. A passing run is green; each dot is one passing test:

tests/test_greeter.py .                              [100%]

1 passed in 0.01s

If you break it (say greet returns "Hi, {name}"), pytest shows an F and (because it rewrites assert statements) the actual vs. expected values, so you see why it failed:

tests/test_greeter.py F                              [100%]

    def test_greet_uses_the_name():
        result = greet("world")
>       assert result == "Hello, world!"
E       AssertionError: assert 'Hi, world' == 'Hello, world!'

1 failed in 0.02s

Add pytest -v for a verbose list of each test by name.

5 · Cover the cases

Good tests check the happy path and the edges. Give each behaviour its own test_ function and name it so a failure reads like a sentence (test_greet_handles_empty_name). When several cases differ only in their inputs, don't copy-paste; parametrize one test to run once per row:

import pytest
from greeter import greet

@pytest.mark.parametrize("name, expected", [
    ("world", "Hello, world!"),
    ("Sam",   "Hello, Sam!"),
    ("",      "Hello, !"),
])
def test_greet(name, expected):
    assert greet(name) == expected

pytest runs this test three times, reporting each row separately, so one failing case doesn't hide the others.

6 · The exit code (why CI cares)

When it finishes, pytest returns an exit code: 0 if every test passed, non-zero if any failed. That single number is the signal the CI pipeline watches in Module 6: green when it's 0, red otherwise. The pipeline runs the very same pytest command you run locally, on a clean machine.
