Lab 4: Test the Game

Make the game's rules testable, then write a pytest suite that proves they work.

1 · Make the logic testable

To test the rules, they must be callable without running the input loop. Split the single tictactoe.py into two files: the logic in a Board class (no I/O), and the game loop that uses it. Then organise the project into src/ and tests/ as you saw in the lecture:

tictactoe/
├── src/
│   ├── board.py        # the rules: a Board class, no input/print (given)
│   └── tictactoe.py    # the game loop, imports Board (given)
├── tests/
│   └── test_board.py   # YOUR pytest tests (Section 2)
└── pyproject.toml      # tells pytest where the code lives

The pyproject.toml at the root puts src/ on the import path, so the imports below stay simple (from board import Board) even though the code now lives in a sub-folder:

# pyproject.toml
[tool.pytest.ini_options]
pythonpath = ["src"]

board.py holds the pure logic, with the anti-diagonal bug already fixed:

# board.py - pure game logic, no I/O
class Board:
    def __init__(self):
        self.cells = ['1', '2', '3', '4', '5', '6', '7', '8', '9']

    def is_valid_move(self, cell):
        return 1 <= cell <= 9 and self.cells[cell - 1] not in ('X', 'O')

    def apply_move(self, cell, player):
        self.cells[cell - 1] = player

    def is_full(self):
        return all(c in ('X', 'O') for c in self.cells)

    def winner(self):
        lines = [
            (0, 1, 2), (3, 4, 5), (6, 7, 8),
            (0, 3, 6), (1, 4, 7), (2, 5, 8),
            (0, 4, 8), (2, 4, 6),
        ]
        for a, b, c in lines:
            if self.cells[a] in ('X', 'O') and self.cells[a] == self.cells[b] == self.cells[c]:
                return self.cells[a]
        return ' '

    def cell_mark(self, cell):
        return self.cells[cell - 1]

tictactoe.py is the input/output, importing Board. The if __name__ == "__main__" guard means importing this file does not start the game (so it never blocks a test):

# tictactoe.py - the game's input/output, using the Board logic
from board import Board


def draw(board):
    for r in range(3):
        print(f" {board.cell_mark(r*3+1)}|{board.cell_mark(r*3+2)}|{board.cell_mark(r*3+3)}")


def main():
    board = Board()
    player = 'X'
    while True:
        draw(board)
        cell = input(f"Player {player}, cell 1-9: ")
        if not cell.isdigit() or not board.is_valid_move(int(cell)):
            print("invalid")
            continue
        board.apply_move(int(cell), player)
        if board.winner() != ' ':
            draw(board)
            print(f"Player {player} wins!")
            break
        if board.is_full():
            draw(board)
            print("Draw")
            break
        player = 'O' if player == 'X' else 'X'


if __name__ == "__main__":
    main()

2 · Write your own tests

Create test_board.py in tests/ and write pytest tests for the Board class, modelled on the lecture (Class 9). Don't copy a finished file: build it from the requirements below. Two tests are given to show the shape: arrange a board with apply_move, then assert on winner() / is_full() / is_valid_move():

# test_board.py
from board import Board


def test_row_win():
    b = Board()
    b.apply_move(1, 'X'); b.apply_move(2, 'X'); b.apply_move(3, 'X')
    assert b.winner() == 'X'


def test_anti_diagonal_win():   # regression test for the Lab 3 bug
    b = Board()
    b.apply_move(3, 'X'); b.apply_move(5, 'X'); b.apply_move(7, 'X')
    assert b.winner() == 'X'
Your suite must also test
  1. A column win (e.g. O on cells 1, 4, 7) is detected.
  2. No winner yet: a board with a couple of moves returns ' ' from winner().
  3. A full board makes is_full() return True (and an empty one returns False).
  4. Move validation: is_valid_move rejects a taken cell and an out-of-range cell (0 or 10), and accepts a free one.

3 · Run the tests

From the project root:

python src/tictactoe.py   # play the game (Ctrl+C to quit)
pytest                  # discover & run every test_*.py under tests/
pytest -v               # the same, listing each test by name
  • A passing run is green and ends with N passed.
  • To see a failure, temporarily change an expected value in a test (or break board.py): pytest turns red and shows the actual vs. expected value. Undo the change to go green again.
  • Running pytest creates a .pytest_cache/ folder and __pycache__/, which you'll git-ignore below.
