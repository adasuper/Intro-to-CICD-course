Resolving Merge Conflicts

What happens when two teammates edit the same lines, and how to reconcile them.

How a conflict arises

Git merges most parallel work automatically. A conflict happens only in one specific situation: two people change the same lines of the same file, based on the same starting point, and both try to share their version. Git cannot know which one is "right", so it stops and asks a human to decide.

Let's walk through it concretely with two teammates, Alice and Bob, who each cloned the same hello repository. Both start from the same commit, in which hello.py's greeting line reads:

print("toolchain OK")

Setup: add your teammate to the repository

For two people to push to the same repository, the owner must first grant the other access. A freshly created Gitee repo is private to its owner, so Bob couldn't push to Alice's hello repo until she adds him as a member. Here is how Alice (the owner) does it:

  1. Open the repository on gitee.com and click the Settings (管理) tab near the top of the repo page.
  2. In the left menu, choose Members (仓库成员管理), then the Developer (开发者) tab. Developers can push code; lower roles like Reporter are read-only and cannot push.
  3. Click Invite member by link (邀请链接) to generate an invitation link.
  4. Copy that link and send it to your teammate (chat, email, etc.).
  5. The teammate opens the link and clicks accept to join. The access only takes effect after they accept.

Once Bob has accepted the link, he can clone the repo over SSH and push to it just like Alice. With both teammates able to push, the stage is set for a conflict.

Roles at a glance

Owner and Admin/Master can manage the repo and its members; Developer can push code; Reporter can only read and open issues. For this exercise, both teammates need Developer or higher.

Reading the conflict markers

Git rewrites the conflicting region of hello.py in place, wrapping both versions in markers. Bob opens the file and sees:

<<<<<<< HEAD
  print("Hi there!")             # Bob's version (his local HEAD)
=======
  print("Hello, world!")         # Alice's version (from the remote)
>>>>>>> origin/master
  • <<<<<<< HEAD begins your side (Bob's current commit).
  • ======= divides the two versions.
  • >>>>>>> origin/master ends their side (the incoming commit).

Resolving it

  1. Edit the file to the single correct result, deleting all three marker lines. Bob talks to Alice and they agree on one wording: 
      print("Hello there!")

    In VS Code, the merge editor shows Accept Current / Accept Incoming / Accept Both buttons above the conflict, but you can always just type the final line by hand, which is often clearest.

The takeaway from the previous lecture's habit holds: had Bob git pulled before starting, he'd have built on Alice's line and likely avoided the clash entirely. git status guides you the whole time: it always lists exactly which files remain unmerged.

Stuck mid-merge?

If a merge gets messy and you want to bail out and start over, git merge --abort returns you to the state just before the pull, nothing lost.
