Ignoring Files with .gitignore

Keeping machine-specific junk and regenerated artifacts out of the repository.

Why ignore files at all?

A repository should hold source, the files a human writes, and nothing that can be regenerated from that source or that only makes sense on one person's machine. Committing everything else causes four concrete problems:

  • Bloat. Generated caches and dependency folders are large or numerous and change constantly, inflating the repository and slowing down every clone.
  • Noise. Generated files flood git status and git diff, burying the real source changes you actually want to review.
  • Non-portability. A .pyc bytecode file is tied to your exact Python version, so it is useless to a teammate on a different setup, yet still downloaded on every pull.
  • Needless conflicts. Files that differ per machine (editor settings, build output) get rewritten by everyone, so they collide constantly, even though nobody meaningfully changed the project.

The fix is a .gitignore file: a list of patterns telling Git which paths to leave untracked. Crucially, .gitignore itself is committed, so the whole team automatically shares the same rules. A typical one for this course's Python project:

# .gitignore for a Python project
__pycache__/    # compiled-bytecode cache folders
*.pyc           # individual bytecode files
.pytest_cache/  # pytest's cache
.venv/          # virtual environment
.vscode/        # per-developer editor settings

What should you ignore?

A good rule of thumb: if a file can be regenerated, is specific to one machine, or should stay secret, ignore it. In practice the things you exclude fall into a few categories:

  • Generated and cached files. Anything Python or your tools produce from the source: the __pycache__/ bytecode-cache folders, *.pyc files, and .pytest_cache/.
  • Editor and IDE settings. Per-developer configuration that differs from machine to machine: .vscode/, JetBrains' .idea/, Vim swap files (*.swp).
  • Operating-system junk. Files the OS sprinkles into folders: .DS_Store on macOS, Thumbs.db on Windows.
  • Downloaded dependencies. Packages a tool can fetch again on demand, so there is no need to store them: e.g. a Python virtual environment .venv/, or node_modules/ in a JavaScript project.
  • Logs and temporary files. Throwaway output such as *.log and *.tmp.
  • Secrets and local-only config. Anything with passwords, API keys, or tokens: .env files, credential files. Never commit these, even by accident.

By contrast, you should always commit the things a teammate genuinely needs: your source files (*.py), the tests, the dependency list (requirements.txt), the README.md, and .gitignore itself. The test is simple: could a teammate re-create everything else from what's committed? If yes, the generated result doesn't belong in the repo.

A cautionary tale: committing .vscode/

It is tempting to git add . and commit everything, including the .vscode/ folder VS Code creates. Here is why that bites you. The folder holds machine-specific settings: for example each developer's .vscode/settings.json records the absolute path to their Python interpreter:

// Alice's .vscode/settings.json
{ "python.defaultInterpreterPath": "C:/Users/Alice/AppData/Local/Programs/Python/Python312/python.exe" }

// Bob's .vscode/settings.json (different machine!)
{ "python.defaultInterpreterPath": "/usr/local/bin/python3" }

Now watch what happens once that file is tracked:

  1. Alice opens the project; VS Code rewrites settings.json with her path. She commits and pushes it.
  2. Bob pulls, opens the project; VS Code immediately rewrites the same line with his path. He commits and pushes.
  3. Alice opens VS Code again the next day, it rewrites the line back to her path. She pushes…

The result is an endless tug-of-war: every teammate's editor keeps overwriting the same line, producing a merge conflict on a file that has nothing to do with the actual program. You waste time resolving conflicts in settings nobody cares about. Listing .vscode/ in .gitignore from the start avoids the whole mess: each person keeps their own local settings, untracked.

Already committed it?

.gitignore only stops Git from tracking files it is not already tracking. If .vscode/ (or a build artifact) is already committed, adding it to .gitignore does nothing until you stop tracking it explicitly:

git rm -r --cached .vscode   # untrack, but keep the files on disk
git commit -m "stop tracking editor settings"

.gitignore syntax in detail

Each non-blank line is one pattern. Patterns are matched relative to the location of the .gitignore file. The rules:

PatternMeaningExample match
# textA comment. Blank lines are ignored too, so you can group rules.n/a
notes.txtMatches a file or folder named notes.txt anywhere in the tree.notes.txt, src/notes.txt
__pycache__/Trailing / matches directories only (and everything inside).__pycache__/, not a file of that name
*.pyc* matches any run of characters except /. Great for extensions.board.pyc, game.pyc
/secret.txtA leading / anchors the pattern to the folder of the .gitignore, so only the root one matches.secret.txt at root, not sub/secret.txt
logs/**/*.log** matches across nested directories.logs/a/b/run.log
file?.txt? matches exactly one character.file1.txt, not file10.txt
*.log
!keep.log		! negates a pattern: it re-includes something a previous line excluded. (You cannot re-include a file if its parent folder is ignored.)ignores every .log except keep.log

Order matters for negation: a later ! line overrides an earlier ignore. For everything else, the patterns are simply a set.
