Intro to CI/CD & DevOps

What the pipeline is, why it exists, and the tools we will use to build one.

Modern software is rarely written once and shipped once. It is changed constantly, by many people, and each change has to be integrated, built, tested, and delivered without breaking what already works. DevOps is the culture and set of practices that make this fast and reliable; CI/CD is the automation at its heart.

Key ideas

DevOps

A way of working that unites development (writing code) and operations (building, testing, releasing, running) so that software moves from a developer's machine to its users smoothly and repeatedly. The goals are short feedback loops, automation of repetitive steps, and shared responsibility for quality.

Continuous Integration (CI)

Every change is merged into a shared repository frequently, and each merge automatically triggers a build and a set of tests. If a change breaks the build or fails a test, the team finds out within minutes instead of weeks. CI is the antidote to "integration hell," where code that worked in isolation collapses when combined.

Continuous Delivery / Deployment (CD)

CD extends CI: once a change passes all checks, the system automatically prepares it for release (delivery) or even releases it (deployment). The payoff is that shipping becomes a routine, low-risk button-press rather than a stressful manual event.

The pipeline, end to end

A CI/CD pipeline is an automated sequence that runs on every change:

source control  →  build  →  test  →  integrate  →  deliver

This course builds each stage from the ground up, and the last lab wires them together into a working pipeline.

The toolchain we will use

  • Git: the version-control system that records every change to the code.
  • Gitee (码云): our remote host for repositories, pull requests, issue tracking, and CI/CD. We use Gitee because it is fast and reliable from within China, where GitHub access is often slow or unstable.
  • A C++ compiler (g++) + Make: to build the project in a structured, repeatable way.
  • Gitee Go: Gitee's built-in CI/CD service, which runs our build and tests automatically on every push.
Course project

Everything is taught around one small program: a console Tic-Tac-Toe game in C++. It starts as a single file you version with Git, becomes a structured, Make-built project, and finishes as a repository whose every commit is automatically built and tested by Gitee Go.

Glossary to remember

  • Repository (repo): a project tracked by Git, including its full history.
  • Commit: a recorded snapshot of changes, with a message.
  • Branch: an independent line of development.
  • Merge: combining the work of two branches.
  • Pipeline: the automated build/test/deliver sequence.
  • Unit test: a small automated check that one piece of code behaves correctly.
  • Artifact: a file produced by the build (e.g. a compiled program).

DevOps technology & tools

Every stage of the loop is backed by a category of technology, and each category has many tools. A typical DevOps toolchain looks like this:

StageTechnology / purposeExample tools
PlanPlanning & issue trackingJira, Trello, Gitee / GitLab Issues
CodeSource control & editorsGit, VS Code, Gitee / GitLab / GitHub
BuildCompiling & build systemsMake, CMake, Maven, Gradle
TestAutomated testingCTest, GoogleTest, Catch2, JUnit, Selenium
ReleaseCI/CD orchestrationGitee Go, Jenkins, GitLab CI, GitHub Actions
DeployDeployment & containersDocker, Kubernetes, Ansible
OperateInfrastructure & configurationKubernetes, Ansible, Terraform
MonitorMonitoring & loggingPrometheus, Grafana, ELK Stack, Nagios

No team uses all of these: the point is that every stage can be automated, and the tools are what wire the stages into one continuous loop.

In this course

We use a small, self-contained slice of this toolchain: Git + Gitee (Plan & Code), Make (Build), a lightweight test program (Test), and Gitee Go (Release / CI). Containerised deploy-and-operate tools such as Docker and Kubernetes are powerful next steps beyond this short course.
