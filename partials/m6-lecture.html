Pipeline Configuration

Configuring a Gitee Go pipeline that tests every change automatically — and then delivers it.

You can already run your tests with one command, pytest. A pipeline hands that command to a server so it runs on every change, on a clean machine, with no one having to remember. Continuous Integration (CI) automatically tests every change the moment it arrives; Continuous Delivery (CD) automatically packages the verified result so it's always ready to ship. We build both on Gitee with Gitee Go.

1 · The CI loop: pull → test → report

On a shared repository, many people push commits. Without automation, a broken change can slip onto master and block the whole team ("but it worked on my machine!"). CI removes that risk: every time someone pushes (or opens a Pull Request), a fresh, clean machine runs the same steps you do:

checkout  (pull the new commit)
   → install   (get the tools: pip install pytest)
   → test      (run the suite: pytest)
   → report    (green = passed, red = a test failed)
  • It runs on a clean machine, so it catches "works on my machine" problems — uncommitted files, a missing dependency, a test that only passed because of leftover state.
  • The result is instant feedback: a green check or a red X next to the commit, with logs you can read.
  • Wired to Pull Requests, it becomes a gate: a PR whose pipeline is red cannot be merged, so broken code never reaches master.

This works only because the tests are scriptable — one command, pytest, that the robot can run exactly as you do.

2 · Configuring the pipeline on Gitee

On gitee.com:

  1. Open your repository → the Services (服务) tab → enable Gitee Go (码云流水线). Free build minutes are generous for a class.
  2. Choose Create pipeline and start from the Python template. Gitee stores the pipeline as a YAML file under a .workflow/ folder in your repo, so it is versioned with your code.
  3. Edit the YAML so its steps match what you run locally, commit it, and the pipeline starts firing on every push.

Here is the whole pipeline file for our project, with every key explained (Gitee's template editor supplies the exact key names, which evolve — map these concepts onto it):

# .workflow/master-pipeline.yml
version: '1.0'
name: master-pipeline
displayName: TicTacToe
triggers:                            # WHEN the pipeline runs
  trigger: auto                      # automatically, with no manual click
  push:
    branches:
      include:
        - master                     # any push to master fires it
stages:                              # ordered phases; each runs only if the previous passed
  - name: test
    displayName: Test
    strategy: naturally               # run this stage's steps in their listed order
    trigger: auto
    steps:
      - step: build@python            # a Python environment, version of your choice
        name: run_tests
        displayName: Run pytest
        pythonVersion: '3.12'
        commands:                     # the same commands you run locally
          - pip install pytest        #   get the test runner
          - pytest                    #   discover & run every test_*.py
  • version / name / displayName — the file-format version, the pipeline's id, and the label shown in the Gitee Go UI.
  • triggers — when it runs. trigger: auto means run automatically; push.branches.include: [master] limits it to pushes to master. (You can add a pull_request trigger to also gate merges.)
  • stages — ordered phases, fail-fast: if the test stage fails the pipeline stops and goes red. strategy: naturally runs a stage's steps in their listed order.
  • step: build@python — the step's type: Gitee Go's Python environment. pythonVersion picks the interpreter (like the Maven template's jdkVersion), so you don't install Python — you just list commands.
  • commands — the shell commands, top to bottom: pip install pytest to get the runner, then pytest. pytest returns a non-zero exit code if any test fails, which fails the step and reddens the pipeline.

Push, then watch it run: green on success, red on failure with the failing assertion in the logs. Break a test on purpose to see red, fix it to see green.

3 · Adding CD: delivering the verified code

CI proves the change is good. CD takes the next step: it automatically turns that verified change into something you can ship. With a server you would deploy (Continuous Deployment); without one, we deliver (Continuous Delivery) — the pipeline publishes a tested, versioned release of the code, so a release is always one step away.

You "update the pipeline accordingly" by adding a stage after test. Because stages are sequential and fail-fast, this release stage only runs when the tests have already passed:

stages:
  - name: test                 # (the CI stage from section 2)
    # ... build@python: pip install pytest, pytest ...

  - name: release              # the CD stage — runs only if test was green
    displayName: Publish
    strategy: naturally
    trigger: auto
    steps:
      - step: publish@release_artifacts    # publish a versioned release
        name: publish_release_artifacts
        displayName: Publish
        version: 1.0.0.0
        autoIncrement: true                # bump the version automatically each release
  • Putting release after test is the gate: stages are fail-fast, so an untested or failing change never reaches this stage.
  • step: publish@release_artifacts — publishes the verified code as a numbered release on Gitee.
  • version + autoIncrement — the release version (1.0.0.0), bumped automatically each run so every delivery is uniquely versioned.
  • The pipeline is now the full loop: pull → test → release. Every push to master yields a tested, versioned release with no manual steps.
Delivery vs deployment

This is Continuous Delivery: the pipeline publishes a verified, versioned release that is always ready to ship. With a server, the same final stage would instead deploy the code to production automatically — full Continuous Deployment. You'll publish a v1.0 release this way in the final project.
