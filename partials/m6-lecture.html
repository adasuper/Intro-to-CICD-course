CI/CD Configuration

Automating the build and tests on every change with Gitee Go.

We now connect everything: a build system (Make), tests, and a remote host (Gitee) become an automated pipeline that runs on every push and protects master from broken code.

Testing pure functions

Because Lab 4 separated the game logic into board.cpp, we can test it directly: no keyboard required. A test program calls functions like checkWinner with known inputs and verifies the outputs. Crucially, it signals success or failure through its exit code: 0 means all tests passed, non-zero means something failed. That exit code is what the pipeline watches.

A test target in the Makefile

We add a rule that compiles the test program against board.cpp, and a test rule that runs it:

test_board: tests/test_board.cpp src/board.cpp
	$(CXX) $(CXXFLAGS) -o test_board tests/test_board.cpp src/board.cpp

test: test_board
	./test_board

Then make test builds and runs the tests. Because the test program returns a non-zero exit code on failure, make test itself fails too, which is exactly the signal CI needs.

Gitee Go

Gitee Go is Gitee's built-in CI/CD. You enable it on the repository, and it stores pipeline definitions as YAML files in a .workflow/ folder. A typical pipeline has stages that run on every push:

checkout → install tools → make → make test
  • Each push triggers the pipeline; you watch it run and read the logs.
  • A passing run is green; a failing one is red.
  • Gitee Go provides free build minutes, generous for a class, so every student can run pipelines.
  • A PR pipeline can gate merges: a Pull Request whose tests fail cannot be merged.
This is CD too

Without Docker, "delivery" here means the pipeline produces a verified, runnable build (an artifact) and you tag a release on Gitee: a reliable, automated path from commit to shippable program.
