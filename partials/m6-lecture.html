Pipeline Configuration

What a pipeline is, how it is built from stages and steps, and how to write one in YAML for Gitee Go.

You can already run your tests with one command, pytest. A pipeline hands that command (and more) to a server so it runs automatically on every change, on a clean machine. This is the engine of CI/CD: Continuous Integration tests every change as it arrives, and Continuous Delivery packages the verified result so it is ready to ship. We build one on Gitee with Gitee Go.

1 · What is a pipeline?

A pipeline is an automated, ordered sequence of work that runs whenever the repository changes. Every push (or Pull Request) triggers it; it checks out the new commit on a fresh machine, runs your build, tests, and delivery, and reports green (all good) or red (something failed). Because it runs on a clean machine every time, it catches "works on my machine" problems and stops broken code from reaching master.

Our pipeline has three phases. Gitee Go draws it left to right like this:

           ┌─ Compile ───────────┐     ┌─ Test ──────────────┐     ┌─ Publish ───────┐
 push ──▶   │  • Python Build     │ ──▶ │  • Python Unit Tests│ ──▶ │  • Publish      │
           │  • Upload Artifact  │     │                     │     │                 │
           └─────────────────────┘     └─────────────────────┘     └─────────────────┘
            steps run in order          runs if Compile passed      runs if Test passed

It reads like a sentence: compile the project and save the result, test it, and only if that passes, publish a release.

2 · Anatomy: stages, steps, and tasks

A pipeline is built from three nested pieces:

  • A stage is a major phase, drawn as one column above (Compile, Test, Publish). Stages run in order and are fail-fast: if one fails, the pipeline stops and the stages after it never run. That ordering is what makes Test a gate before Publish.
  • A step is one box inside a stage (Python Build, Upload Artifact, …). A stage runs its steps top to bottom. Compile above has two steps; Test has one.
  • A task (Gitee calls it a plugin) is what a step actually does: "run Python commands", "run unit tests", "publish a release", and so on. In the YAML a step names its task with step: build@python, step: ut@python, or step: publish@release_artifacts.

So the hierarchy is pipeline → stages → steps → one task each. Steps can also hand data forward: the Upload Artifact step saves the project as an artifact that the Publish stage later releases.

"Compile" for Python?

Python isn't compiled to a machine-code binary, but the Compile stage still earns its name: python3 -m compileall src byte-compiles every file in src/, which fails fast on any syntax error before a single test runs. The stage also installs dependencies and packages the source as an artifact.

3 · YAML in sixty seconds

Gitee Go stores the pipeline as a YAML file. YAML is a plain-text format for configuration, built from key: value pairs. Three rules cover almost everything:

  • Indentation shows nesting (spaces only, never tabs): a key indented under another belongs to it.
  • A leading - makes a list item.
  • # starts a comment; blank lines are ignored.
name: master-pipeline        # a key and its (string) value
pythonVersion: '3.13'        # quotes keep it a string, not the number 3.13
stages:                      # this key's value is a list…
  - name: test               # "-" starts one list item (itself a mapping)
    steps:                   # nested under this stage
      - pip install pytest   # a list of two commands
      - pytest

Values are usually unquoted; quote one to keep it a string (so '3.13' isn't read as a number and '1.0' keeps its trailing zero). That is enough YAML to read and edit any pipeline.

4 · The pipeline file, explained

Here is the real pipeline file behind that diagram: Gitee's Python template, filled in for our project. (Gitee's editor also writes a few empty default fields such as executor: [], checkpoints: [], caches: [] and notify: []; they're trimmed here, so just leave them as the editor wrote them.)

# .workflow/master-pipeline.yml
version: '1.0'
name: master-pipeline
displayName: MasterPipeline
triggers:                              # WHEN it runs: automatically, on push to master
  trigger: auto
  push:
    branches:
      include:
        - master
stages:
  - name: compile                      # Stage 1: install deps, byte-compile, package
    displayName: Compile
    strategy: naturally                # run this stage's steps in order
    trigger: auto
    steps:
      - step: build@python             # task: a Python 3.13 environment
        name: build_python
        displayName: Python Build
        pythonVersion: '3.13'
        commands:
          - python3 -m pip install --upgrade pip
          - pip3 config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple   # China mirror
          - pip3 install -r requirements.txt
          - python3 -m compileall src   # byte-compile src/ (fails on a syntax error)
        artifacts:                      # capture the project as an artifact…
          - name: BUILD_ARTIFACT
            path:
              - ./
      - step: publish@general_artifacts # task: save that artifact as "output"
        name: publish_general_artifacts
        displayName: Upload Artifact
        dependArtifact: BUILD_ARTIFACT
        artifactName: output
        dependsOn: build_python
  - name: test                         # Stage 2: the CI gate
    displayName: Test
    strategy: naturally
    trigger: auto
    steps:
      - step: ut@python                # task: unit tests + a test report
        name: unit_test_python
        displayName: Python Unit Tests
        pythonVersion: '3.13'
        commands:
          - pip3 config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
          - pip3 install -r requirements.txt
          - pytest --html=report/index.html   # run tests, write an HTML report
        report:                         # surface that report on the run page
          path: report
          index: index.html
  - name: release                      # Stage 3: CD, only if Test passed
    displayName: Publish
    strategy: naturally
    trigger: auto
    steps:
      - step: publish@release_artifacts
        name: publish_release_artifacts
        displayName: Publish
        dependArtifact: output
        version: 1.0.0.0
        autoIncrement: true            # bump the version each release
  • version / name / displayName: the file-format version, the pipeline's id, and the label shown in the UI.
  • triggers says when it runs: trigger: auto + push.branches.include: [master] means "automatically, on any push to master." (Add a pull_request trigger to gate merges too.)
  • strategy: naturally runs a stage's steps in their listed order. Stages themselves run top-to-bottom and fail-fast.
  • step: picks the task: build@python runs commands in a Python 3.13 environment, ut@python runs unit tests and captures a report, and publish@general_artifacts / publish@release_artifacts handle the artifact and the release.
  • commands: the Compile step upgrades pip, points it at the Tsinghua mirror (fast from China), installs requirements.txt, then python3 -m compileall src byte-compiles your code (a free syntax check before any test runs).
  • report: the Test step runs pytest --html=report/index.html, and the report: block surfaces that HTML report on the run page, so you can browse failures without scrolling the raw log.
  • dependsOn / dependArtifact: order steps and pass the saved output artifact from Upload Artifact through to Publish.

5 · Three pipelines: master, branch, and PR

The file above is the master pipeline: it triggers on a push to master. But work at different points needs different treatment, so Gitee Go lets you configure three pipelines, each with its own trigger:

PipelineTriggered when…Typical stages
Mastera push or merge lands on masterCompile → Test → Publish
Branchyou push to a feature branch (not master)Compile → Test
PRa Pull Request targeting master is opened or updatedCompile → Test (the merge gate)
  • Only the master pipeline publishes. You release from master because that's the finished, reviewed line; the branch and PR pipelines stop at Test; you don't ship unfinished or unreviewed work.
  • The branch pipeline gives you fast feedback while you develop on a feature branch: every push builds and tests your work-in-progress, so you catch breakage early.
  • The PR pipeline is the merge gate from Module 4: it runs build + test against the proposed merge, and a red result blocks the Pull Request from being merged, so broken code never reaches master.

It's the same building blocks (stages, steps, tasks) each time; only the trigger and whether there's a Publish stage differ. Our file's triggers: push: branches: include: [master] is what makes it the master pipeline; a branch pipeline would list other branches, and a PR pipeline uses a pull_request trigger.

6 · Run it on Gitee, red then green

  1. In your repo, open the Services (服务) tab → enable Gitee Go, and Create pipeline from the Python template (which gives you exactly the Compile / Test / Publish shape above). Gitee saves it under .workflow/ in your repo.
  2. Commit & push, then watch it run: green when pytest passes, red when it fails (with the failing assertion in the logs).
  3. Break a test on purpose to see Test go red and Publish skipped; fix it to go green.

Because Test sits before Publish and stages are fail-fast, a failing test blocks the release; that is the whole point. The Publish stage is the CD half: it publishes a tested, versioned release with no manual steps.
