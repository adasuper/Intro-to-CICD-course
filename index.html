Module 1 · Lecture · Class 1

Intro to CI/CD & DevOps

What the pipeline is, why it exists, and the tools we will use to build one.

Modern software is rarely written once and shipped once. It is changed constantly, by many people, and each change has to be integrated, built, tested, and delivered without breaking what already works. DevOps is the culture and set of practices that make this fast and reliable; CI/CD is the automation at its heart.

Key ideas

DevOps

A way of working that unites development (writing code) and operations (building, testing, releasing, running) so that software moves from a developer's machine to its users smoothly and repeatedly. The goals are short feedback loops, automation of repetitive steps, and shared responsibility for quality.

Continuous Integration (CI)

Every change is merged into a shared repository frequently, and each merge automatically triggers a build and a set of tests. If a change breaks the build or fails a test, the team finds out within minutes instead of weeks. CI is the antidote to "integration hell," where code that worked in isolation collapses when combined.

Continuous Delivery / Deployment (CD)

CD extends CI: once a change passes all checks, the system automatically prepares it for release (delivery) or even releases it (deployment). The payoff is that shipping becomes a routine, low-risk button-press rather than a stressful manual event.

The pipeline, end to end

A CI/CD pipeline is an automated sequence that runs on every change:

source control  →  build  →  test  →  integrate  →  deliver

This course builds each stage from the ground up, and the last lab wires them together into a working pipeline.

The toolchain we will use

  • Git — the version-control system that records every change to the code.
  • Gitee (码云) — our remote host for repositories, pull requests, issue tracking, and CI/CD. We use Gitee because it is fast and reliable from within China, where GitHub access is often slow or unstable.
  • A C++ compiler (g++) + CMake — to compile the project in a structured, repeatable way.
  • Gitee Go — Gitee's built-in CI/CD service, which runs our build and tests automatically on every push.
Course project

Everything is taught around one small program: a console Tic-Tac-Toe game in C++. It starts as a single file you version with Git, becomes a structured CMake project, and finishes as a repository whose every commit is automatically built and tested by Gitee Go.

Glossary to remember

  • Repository (repo) — a project tracked by Git, including its full history.
  • Commit — a recorded snapshot of changes, with a message.
  • Branch — an independent line of development.
  • Merge — combining the work of two branches.
  • Pipeline — the automated build/test/deliver sequence.
  • Unit test — a small automated check that one piece of code behaves correctly.
  • Artifact — a file produced by the build (e.g. a compiled program).

DevOps technology & tools

Every stage of the loop is backed by a category of technology, and each category has many tools. A typical DevOps toolchain looks like this:

StageTechnology / purposeExample tools

CodeSource control & editorsGit, VS Code, Gitee / GitLab / GitHub

In this course

We use a small, self-contained slice of this toolchain: Git + Gitee (Plan & Code), CMake (Build), a lightweight CTest harness (Test), and Gitee Go (Release / CI). Containerised deploy-and-operate tools such as Docker and Kubernetes are powerful next steps beyond this short course.

Git Basics

How Git tracks your work across four locations — the mental model behind Lab 1.

Git is a version-control system: it records snapshots of your project over time so you can review history, undo mistakes, and collaborate without overwriting each other's work. The key to using it confidently is understanding where a file lives at any moment.

The four locations

Every change moves through four places. Today's lab is built entirely around tracking files across them:

  • Workspace (working directory) — the actual files you edit on disk.
  • Staging Area (index) — a holding area for changes you have marked to include in the next commit.
  • Local Repository — the committed history stored on your own machine.
  • Remote Repository — the shared copy on Gitee that your team pulls from and pushes to.

The core commands

git clone <url>     # copy a remote repo to your workspace
git status          # what changed, and where it lives now
git add <file>       # workspace  → staging area
git reset           # staging area → workspace (unstage)
git commit          # staging area → local repository
git push            # local repo  → remote repository
git pull            # remote repo → local + workspace
git log             # view commit history
git diff            # view exact changes

The journey of a change

You edit a file (workspace) → git add it (staging) → git commit it (local repo) → git push it (remote). Each command moves the change one step closer to being shared. Knowing which command moves a file between which two locations is the whole game — and the worksheet in Lab 1 makes you trace it explicitly.

Good habits

  • Commit small, logical units of work — not "everything at once."
  • Write clear messages: "add input prompt", not "stuff".
  • Run git status often; it is your map.
  • Keep a useful README.md describing the project.

.gitignore & Conflict Resolution

Keeping junk out of the repository, and reconciling changes when two people edit the same lines.

What does not belong in a repository

A repository should contain source, not the things you can regenerate from it. Compiled binaries, object files, and build folders bloat the repo, cause needless conflicts, and differ per machine. You exclude them with a .gitignore file.

# .gitignore for a C++ / CMake project
build/
*.o
*.exe
*.out
ttt
.vscode/

Patterns match file or folder names; a trailing / matches a directory. .gitignore itself is committed, so the whole team shares the same rules.

Important

.gitignore only stops Git from tracking files it is not already tracking. If you already committed a build artifact, you must stop tracking it explicitly:

git rm --cached <file>   # untrack but keep on disk

How conflicts happen

When two people change the same lines of the same file and both try to push, Git cannot decide which version wins. The second push is rejected (a "non-fast-forward" error). After git pull, Git marks the clash with conflict markers:

<<<<<<< HEAD
your version of the line
=======
their version of the line
>>>>>>> origin/main

Resolving a conflict

  1. git pull — bring in the remote changes; Git reports the conflict.
  2. Open the file (VS Code's merge editor is ideal) and edit it so it contains the correct combined result. Delete all three marker lines.
  3. git add <file> to mark it resolved.
  4. git commit then git push.

git status guides you the entire time — it lists exactly which files are still in conflict.

Git Branching

Working on features in parallel without destabilising the main line.

A branch is an independent line of development. It lets you build a new feature while main stays stable and shippable. When the feature is ready, you merge it back.

The mental model

A branch is just a movable pointer to a commit. Creating a branch is cheap; switching between them changes which version of the files you see. The discipline is simple: keep main always working, do risky work on feature branches.

Core commands

git branch                 # list branches
git checkout -b feature/x    # create and switch to a new branch
git switch main             # switch back to main
git merge feature/x        # merge a branch into the current one
git branch -d feature/x     # delete a merged local branch
git push -u origin feature/x # publish a branch to the remote

Fast-forward vs. merge commit

If main hasn't moved since you branched, Git can simply slide its pointer forward — a fast-forward. If both branches have new commits, Git creates a merge commit that ties the two histories together (and may require resolving a conflict, exactly as in Lab 2).

The Pull Request workflow on Gitee

  1. Push your feature branch to Gitee.
  2. Open a Pull Request (PR) proposing to merge it into main.
  3. A teammate reviews the changes and comments.
  4. Merge the PR; delete the branch; everyone pulls the updated main.

PRs are where code review happens, and — once we add CI in Module 6 — where automated tests gate the merge. PRs can also be linked to issues so a merge automatically closes the task it addressed.

CMake

Why manual g++ doesn't scale, and how to describe a build once and run it anywhere.

As soon as a project has more than one source file, typing g++ commands by hand becomes error-prone and unrepeatable. CMake lets you describe your build in one file; it then generates the right commands for whatever compiler and platform you're on.

The anatomy of CMakeLists.txt

cmake_minimum_required(VERSION 3.16)
project(tictactoe CXX)
set(CMAKE_CXX_STANDARD 17)

add_library(game src/board.cpp)          # reusable game logic
target_include_directories(game PUBLIC include)

add_executable(tictactoe src/main.cpp)    # the playable program
target_link_libraries(tictactoe PRIVATE game)

Out-of-source builds

CMake keeps all generated files in a separate build/ folder, so your source tree stays clean (and build/ goes in .gitignore):

cmake -B build        # configure: generate the build system
cmake --build build   # compile

Why split a library from the executable?

We move the pure game logic (board state, move validation, win detection) into a game library, and keep only input/output in the executable. This separation is what makes the logic testable — in Module 6 the automated pipeline links tests against the game library without needing a keyboard. A clean structure today is what makes CI possible tomorrow:

tictactoe/
├── include/board.h
├── src/board.cpp      # pure logic → library
├── src/main.cpp       # I/O loop → executable
├── tests/test_board.cpp
└── CMakeLists.txt

  2. Create a branch feature/cmake, commit the restructure, push it, and open a Pull Request on Gitee (reinforcing Lab 3). Merge it into main.

Module 6 · Lecture · Class 11

CI/CD Configuration

Automating the build and tests on every change with Gitee Go.

We now connect everything: a build system (CMake), tests, and a remote host (Gitee) become an automated pipeline that runs on every push and protects main from broken code.

Testing pure functions

Because Lab 4 moved the game logic into a library, we can test it directly — no keyboard required. A test program calls functions like checkWinner with known inputs and verifies the outputs. Crucially, it signals success or failure through its exit code: 0 means all tests passed, non-zero means something failed. That exit code is what the pipeline watches.

CTest

CMake's testing tool, CTest, runs your test programs and reports pass/fail:

enable_testing()
add_executable(test_board tests/test_board.cpp)
target_link_libraries(test_board PRIVATE game)
add_test(NAME board_tests COMMAND test_board)

Then ctest --test-dir build runs them.

Gitee Go

Gitee Go is Gitee's built-in CI/CD. You enable it on the repository, and it stores pipeline definitions as YAML files in a .workflow/ folder. A typical pipeline has stages that run on every push:

checkout → install tools → cmake configure → build → ctest
  • Each push triggers the pipeline; you watch it run and read the logs.
  • A passing run is green; a failing one is red.
  • Gitee Go provides free build minutes — generous for a class — so every student can run pipelines.
  • A PR pipeline can gate merges: a Pull Request whose tests fail cannot be merged.
This is CD too

Without Docker, "delivery" here means the pipeline produces a verified, runnable build (an artifact) and you tag a release on Gitee — a reliable, automated path from commit to shippable program.

Lab 5 — Build & Test Pipeline on Gitee Go

Add unit tests, wire them into CTest, then automate everything in a pipeline. Watch it go red, then green.

1 · Write a test program

Create tests/test_board.cpp — a tiny, dependency-free harness (no external framework needed, which avoids download problems):

#include "board.h"
#include <iostream>
static int failures = 0;
#define CHECK(c) do{ if(!(c)){ std::cerr<<"FAIL: " #c <<" @"<<__LINE__<<"\n"; ++failures; } }while(0)

int main(){
  Board top{{'X','X','X',' ',' ',' ',' ',' ',' '}};
  CHECK(checkWinner(top)=='X');                 // row win
  Board col{{'O',' ',' ','O',' ',' ','O',' ',' '}};
  CHECK(checkWinner(col)=='O');                 // column win
  Board diag{{'X',' ',' ',' ','X',' ',' ',' ','X'}};
  CHECK(checkWinner(diag)=='X');                // diagonal win
  Board none{{'X','O','X',' ',' ',' ',' ',' ',' '}};
  CHECK(checkWinner(none)==' ');                // no winner
  Board draw{{'X','O','X','X','O','O','O','X','X'}};
  CHECK(isFull(draw) && checkWinner(draw)==' '); // draw
  Board g{{'X',' ',' ',' ',' ',' ',' ',' ',' '}};
  CHECK(!isValidMove(g,0)); CHECK(isValidMove(g,1));

  if(failures==0){ std::cout<<"All tests passed!\n"; return 0; }
  std::cerr<<failures<<" test(s) failed.\n"; return 1;
}

2 · Wire it into CMake / CTest

Add to CMakeLists.txt, then verify locally with ctest:

enable_testing()
add_executable(test_board tests/test_board.cpp)
target_link_libraries(test_board PRIVATE game)
add_test(NAME board_tests COMMAND test_board)
cmake -B build && cmake --build build
ctest --test-dir build --output-on-failure

3 · Create the Gitee Go pipeline

Enable Gitee Go on your repo and add a pipeline. Start from Gitee's shell/build template and set its steps to the commands below (the exact YAML keys come from the template editor — adjust to match the current Gitee Go interface). The pipeline should run the same steps your machine does:

# .workflow/  — illustrative shape; build the real one from Gitee's template
name: build-and-test
trigger: [push, pull_request]
stages:
  - name: build-test
    steps:
      - apt-get install -y cmake g++     # ensure tools
      - cmake -B build
      - cmake --build build
      - ctest --test-dir build --output-on-failure

4 · Make it go red, then green

  1. Push your work and watch the pipeline turn green.
  2. Deliberately break a test (e.g. change an expected winner) and push — watch it turn red and read the failure in the logs.
  3. Fix it and push again → green.
  4. (Optional) Configure the PR pipeline so a Pull Request can't merge while tests fail.
Done when

Every push to your repository automatically builds the project and runs the tests on Gitee Go, and you have seen a full red → green cycle.
