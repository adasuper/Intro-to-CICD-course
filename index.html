Module 1 · Lecture · Class 1

Intro to CI/CD & DevOps

What the pipeline is, why it exists, and the tools we will use to build one.

Modern software is rarely written once and shipped once. It is changed constantly, by many people, and each change has to be integrated, built, tested, and delivered without breaking what already works. DevOps is the culture and set of practices that make this fast and reliable; CI/CD is the automation at its heart.

Key ideas

DevOps

A way of working that unites development (writing code) and operations (building, testing, releasing, running) so that software moves from a developer's machine to its users smoothly and repeatedly. The goals are short feedback loops, automation of repetitive steps, and shared responsibility for quality.

Continuous Integration (CI)

Every change is merged into a shared repository frequently, and each merge automatically triggers a build and a set of tests. If a change breaks the build or fails a test, the team finds out within minutes instead of weeks. CI is the antidote to "integration hell," where code that worked in isolation collapses when combined.

Continuous Delivery / Deployment (CD)

CD extends CI: once a change passes all checks, the system automatically prepares it for release (delivery) or even releases it (deployment). The payoff is that shipping becomes a routine, low-risk button-press rather than a stressful manual event.

The pipeline, end to end

A CI/CD pipeline is an automated sequence that runs on every change:

source control  →  build  →  test  →  integrate  →  deliver

This course builds each stage from the ground up, and the last lab wires them together into a working pipeline.

The toolchain we will use

  • Git: the version-control system that records every change to the code.
  • Gitee (码云): our remote host for repositories, pull requests, issue tracking, and CI/CD. We use Gitee because it is fast and reliable from within China, where GitHub access is often slow or unstable.
  • A C++ compiler (g++) + Make: to build the project in a structured, repeatable way.
  • Gitee Go: Gitee's built-in CI/CD service, which runs our build and tests automatically on every push.
Course project

Everything is taught around one small program: a console Tic-Tac-Toe game in C++. It starts as a single file you version with Git, becomes a structured, Make-built project, and finishes as a repository whose every commit is automatically built and tested by Gitee Go.

Glossary to remember

  • Repository (repo): a project tracked by Git, including its full history.
  • Commit: a recorded snapshot of changes, with a message.
  • Branch: an independent line of development.
  • Merge: combining the work of two branches.
  • Pipeline: the automated build/test/deliver sequence.
  • Unit test: a small automated check that one piece of code behaves correctly.
  • Artifact: a file produced by the build (e.g. a compiled program).

Every stage of the loop is backed by a category of technology, and each category has many tools. A typical DevOps toolchain looks like this:

5 · Create a Gitee account & SSH key

Gitee hosts your repositories and runs the CI pipeline. To push your commits up to Gitee, your computer has to prove who it is every time it connects. There are two ways to do that, HTTPS and SSH, and it is worth understanding the difference before you set one up.

HTTPS vs. SSH: two ways to authenticate

Both transport the exact same Git data; they only differ in how the server checks that the connection is allowed.

HTTPSSSH
Remote URL looks likehttps://gitee.com/user/repo.gitgit@gitee.com:user/repo.git
How you prove it's youUsername + password / access token, typed (or cached) on each push.A cryptographic key pair stored once on your machine, no password typed.
Setup effortNone up front, but you re-enter credentials (or manage a token) repeatedly.A few minutes once; after that, pushing is friction-free.
Best whenOne-off clones, machines you don't control, networks that block SSH.Your own daily-driver machine, which is our case.

We use SSH in this course: you set it up once and never type a password to push again.

How SSH keys work

SSH uses a matched key pair: a private key that stays secret on your computer, and a public key you give to Gitee. When you connect, Gitee challenges your machine to prove it holds the matching private key, without the private key ever leaving your computer. The public key is safe to share; the private key (the file without .pub) must never be copied or posted anywhere.

↗ Register on gitee.com
  1. Create and verify an account at gitee.com.
  2. In Git Bash, generate a key pair (press Enter at every prompt to accept the defaults): 
    ssh-keygen -t ed25519 -C "you@example.com"

    Breaking the command down:

    • ssh-keygen: the program that creates a new SSH key pair.
    • -t ed25519: the key type (algorithm). Ed25519 is the modern, fast, secure default.
    • -C "you@example.com": a comment label attached to the key so you can recognise it later in Gitee's list. It does not have to be a real email; it's just a tag.

    This writes two files into ~/.ssh/: id_ed25519 (your private key, keep secret) and id_ed25519.pub (your public key, safe to share). The prompts ask where to save it (Enter = default) and for an optional passphrase that encrypts the private key on disk.

  3. Display and copy the public key: note the .pub extension; never copy the other file: 
    cat ~/.ssh/id_ed25519.pub

    cat prints a file's contents to the screen. Select the whole line it outputs (it starts with ssh-ed25519 and ends with your comment) and copy it.

  4. On Gitee: avatar → Settings → SSH Public Keys → Add Public Key → paste it and save. This tells Gitee to trust any machine that holds the matching private key.
  5. Test the connection: 
    ssh -T git@gitee.com

    ssh opens a secure connection; -T skips requesting an interactive terminal (Gitee doesn't offer a shell, only Git); git@gitee.com is the user git on the host gitee.com. A successful run greets you by your username: that confirms your key is recognised.

First-connection prompt

The first time you run ssh -T, you'll see "The authenticity of host 'gitee.com' can't be established… continue connecting (yes/no)?", type yes. This records Gitee's fingerprint so future connections are trusted automatically.

"Does not provide shell access" is success

A correct test prints something like "Hi user(@user)! You've successfully authenticated, but GITEE.COM does not provide shell access." That is not an error. The first half means your key worked and Gitee knows who you are. The second half is normal: the git account exists only to handle push/pull, not to give you a command prompt, so it logs you out instead of opening a shell (which is why we pass -T). A real failure looks different: Permission denied (publickey).

Git Basics

How Git tracks your work across four locations: the mental model behind Lab 1.

Git is a version-control system: it records snapshots of your project over time so you can review history, undo mistakes, and collaborate without overwriting each other's work. The key to using it confidently is understanding where a file lives at any moment.

The four locations

Every change moves through four places. Today's lab is built entirely around tracking files across them:

  • Workspace (working directory): the actual files you edit on disk.
  • Staging Area (index): a holding area for changes you have marked to include in the next commit.
  • Local Repository: the committed history stored on your own machine.
  • Remote Repository: the shared copy on Gitee that your team pulls from and pushes to.

The core commands

Use this block as a quick map of which command moves a change between which two locations, then read the detail below for when and how to reach for each one.

git clone <url>     # copy a remote repo to your workspace
git status          # what changed, and where it lives now
git add <file>       # workspace  → staging area
git reset           # staging area → workspace (unstage)
git commit          # staging area → local repository
git push            # local repo  → remote repository
git pull            # remote repo → local + workspace
git log             # view commit history
git diff            # view exact changes

The examples below all use the hello repository you pushed to Gitee in the Setup Lab smoke test (git@gitee.com:adasuper/hello.git, swap in your own username). Imagine you are coming back to it on a fresh machine to make a small change.

git clone <url>

When: once per project, to make a local copy of a repository that already exists on Gitee.

How: run it in the folder where you want the project to land. It creates a new sub-folder, downloads the full history, and wires up the remote (named origin) for you, so git init + git remote add are unnecessary.

Example: grab your hello repo onto a new machine and step into it:

git clone git@gitee.com:adasuper/hello.git
cd hello

git status

When: constantly, before and after almost every other command. It is your map of where each file currently lives.

How: it needs no arguments and changes nothing; it lists files that are modified but unstaged, files staged for the next commit, and files Git isn't tracking yet.

Example: after editing hello.cpp to print a friendlier message:

git status
# Changes not staged for commit:
#   modified:   hello.cpp

git add <file>

When: after editing, to mark exactly which changes belong in your next commit (workspace → staging).

How: name specific files to stage them deliberately, or use . to stage everything changed. Staging is what lets you commit two edits separately even if you made them at the same time.

Example: stage your edited hello.cpp:

git add hello.cpp         # just this file
git add .                  # everything changed in the hello folder

git reset <file>

When: you staged something by mistake and want to take it back out of the next commit (staging → workspace).

How: it unstages the file while keeping your edits: your file on disk is untouched, it just won't be in the next commit. It is the exact undo of git add (which is why Lab 1 has you add then unstage).

Example: you staged hello.cpp but realise you aren't done editing it:

git reset hello.cpp        # back to unstaged; your edits remain

git reset --soft vs git reset --hard

git reset can also rewind a whole commit by pointing the branch at an earlier one. The mode flag decides how far the undo reaches across the three locations, and this is where you can lose work, so understand it before using it.

  • --soft: moves the branch back, but keeps everything staged. The commit is undone; its changes sit ready in the staging area as if you'd just run git add. Use it to redo a commit message or fold several commits into one. Nothing is lost.
  • --mixed (the default, what you get with no flag): moves the branch back and unstages the changes, but leaves your edits in the workspace. This is the same family as the file-level git reset <file> above. Nothing is lost.
  • --hard: moves the branch back and throws away the changes in both the staging area and the workspace, resetting your files on disk to match the target commit. This permanently deletes uncommitted work: there is no undo.
git reset --soft HEAD~1    # undo last commit, keep changes staged
git reset HEAD~1           # (--mixed) undo last commit, keep changes in workspace
git reset --hard HEAD~1    # undo last commit AND discard the changes: careful!
Handle --hard with care

--hard is the only one of the three that destroys work you haven't committed. Reach for --soft or the default --mixed unless you are absolutely certain you want those edits gone. HEAD~1 means "one commit before the current tip"; HEAD~2 would go back two, and so on.

git commit -m "message"

When: once a staged set of changes forms one complete, logical unit of work (staging → local repository).

How: always include a clear message with -m. The commit is a permanent snapshot in your local history: it is not on Gitee yet until you push.

Example: record your greeting change as a commit:

git commit -m "print a friendlier greeting"

git push

When: after committing, to publish your local commits so teammates and the CI pipeline can see them (local → remote).

How: the first push of a new branch needs -u origin <branch> to link it; after that, a bare git push is enough.

Example: the smoke test already ran the first form, so from now on a bare push is all you need:

git push -u origin master    # first time (done in the smoke test)
git push                      # every push to hello after that

git pull (and git fetch)

When: before you start working, and whenever a teammate has pushed to hello, to bring their commits into your copy.

How: run it with a clean workspace (commit or stash your own changes first) to avoid merge conflicts. The distinction matters: git fetch only downloads new commits into your local repository (remote → local repo) and leaves your working files untouched, so you can inspect what changed first. git pull is fetch followed by merge: it goes one step further and updates the files on your disk too (remote → local repo → workspace).

Example: sync the hello repo before adding your next change:

git fetch                   # download new commits, hello.cpp on disk unchanged
git pull                    # download AND update hello.cpp on disk

git log

When: any time you need to see the history of a repository: what was changed, by whom, and when.

How: it lists past commits newest-first with author, date, and message. Add --oneline for a compact one-row-per-commit view.

Example: review the history of hello after your new commit:

git log --oneline
# a1b2c3d  print a friendlier greeting
# e4f5a6b  first commit: hello

git diff

When: to review the exact line-by-line changes you've made, typically right before git add or git commit.

How: git diff alone shows unstaged edits (workspace vs. staging); git diff --staged shows what's already staged for the next commit (staging vs. last commit).

Example: check what you changed in hello.cpp before staging it:

git diff                    # unstaged edits to hello.cpp
git diff --staged           # what the next commit will record

The journey of a change

You edit a file (workspace) → git add it (staging) → git commit it (local repo) → git push it (remote). Each command moves the change one step closer to being shared. Knowing which command moves a file between which two locations is the whole game, and the worksheet in Lab 1 makes you trace it explicitly.

Good habits

  • Commit small, logical units of work: not "everything at once."
    A commit that does one thing is easy to understand, and if it introduces a bug you can undo just that change without losing unrelated work. A giant "did lots of stuff" commit hides what actually happened and is painful to reverse.
  • Write clear messages: "add input prompt", not "stuff".
    Months later, the message is often the only clue to why a change was made. A good message lets you (and teammates) scan the history and find the right commit without reading every line of code.
  • Run git status often; it is your map.
    It tells you exactly which files are modified, staged, or untracked before you act. Checking first prevents the common mistakes of committing the wrong file or forgetting to stage one you meant to include.
  • Always git pull before you start working, and pull once more right before you push.
    Pulling first means you build on your teammates' latest work instead of an outdated copy. Pulling again just before pushing catches anything that landed while you were coding, so conflicts surface locally where they are easy to fix, rather than your push being rejected because the remote moved ahead.
  • Keep a useful README.md describing the project.
    It is the first thing anyone (including future you) reads to learn what the project does and how to build and run it. A clear README turns a pile of files into a project someone can actually pick up.

Ignoring Files with .gitignore

Keeping machine-specific junk and regenerated artifacts out of the repository.

Why ignore files at all?

A repository should hold source, the files a human writes, and nothing that can be regenerated from that source or that only makes sense on one person's machine. Committing everything else causes four concrete problems:

  • Bloat. Compiled binaries and build folders are large and change on every build, inflating the repository and slowing down every clone.
  • Noise. Generated files flood git status and git diff, burying the real source changes you actually want to review.
  • Non-portability. A binary you compiled won't run on a teammate's different OS, it is useless to them, yet still downloaded on every pull.
  • Needless conflicts. Files that differ per machine (editor settings, build output) get rewritten by everyone, so they collide constantly, even though nobody meaningfully changed the project.

The fix is a .gitignore file: a list of patterns telling Git which paths to leave untracked. Crucially, .gitignore itself is committed, so the whole team automatically shares the same rules. A typical one for this course's C++ project:

# .gitignore for a C++ project
*.o             # object files
*.exe           # Windows executables
*.out           # a.out-style binaries
ttt             # our compiled game binary
.vscode/        # per-developer editor settings

What should you ignore?

A good rule of thumb: if a file can be regenerated, is specific to one machine, or should stay secret, ignore it. In practice the things you exclude fall into a few categories:

  • Build output and compiled artifacts. Anything your compiler or build tool produces from the source: executables and object files: *.o, *.exe, *.out, a.out, and our game binary ttt.
  • Editor and IDE settings. Per-developer configuration that differs from machine to machine: .vscode/, JetBrains' .idea/, Vim swap files (*.swp).
  • Operating-system junk. Files the OS sprinkles into folders: .DS_Store on macOS, Thumbs.db on Windows.
  • Downloaded dependencies. Packages a tool can fetch again on demand, so there is no need to store them: e.g. vcpkg_installed/, or node_modules/ in a JavaScript project.
  • Logs and temporary files. Throwaway output such as *.log and *.tmp.
  • Secrets and local-only config. Anything with passwords, API keys, or tokens: .env files, credential files. Never commit these, even by accident.

By contrast, you should always commit the things a teammate genuinely needs: your source files (*.cpp, *.h), the build instructions (Makefile), tests, the README.md, and .gitignore itself. The test is simple: could a teammate rebuild this from what's committed? If yes, the generated result doesn't belong in the repo.

A cautionary tale: committing .vscode/

It is tempting to git add . and commit everything, including the .vscode/ folder VS Code creates. Here is why that bites you. The folder holds machine-specific settings: for example each developer's .vscode/settings.json records the absolute path to their compiler:

// Alice's .vscode/settings.json
{ "C_Cpp.default.compilerPath": "C:/msys64/ucrt64/bin/g++.exe" }

// Bob's .vscode/settings.json (different machine!)
{ "C_Cpp.default.compilerPath": "/usr/local/bin/g++" }

Now watch what happens once that file is tracked:

  1. Alice opens the project; VS Code rewrites settings.json with her path. She commits and pushes it.
  2. Bob pulls, opens the project; VS Code immediately rewrites the same line with his path. He commits and pushes.
  3. Alice opens VS Code again the next day, it rewrites the line back to her path. She pushes…

The result is an endless tug-of-war: every teammate's editor keeps overwriting the same line, producing a merge conflict on a file that has nothing to do with the actual program. You waste time resolving conflicts in settings nobody cares about. Listing .vscode/ in .gitignore from the start avoids the whole mess: each person keeps their own local settings, untracked.

Already committed it?

.gitignore only stops Git from tracking files it is not already tracking. If .vscode/ (or a build artifact) is already committed, adding it to .gitignore does nothing until you stop tracking it explicitly:

git rm -r --cached .vscode   # untrack, but keep the files on disk
git commit -m "stop tracking editor settings"

.gitignore syntax in detail

Each non-blank line is one pattern. Patterns are matched relative to the location of the .gitignore file. The rules:

Resolving Merge Conflicts

What happens when two teammates edit the same lines, and how to reconcile them.

How a conflict arises

Git merges most parallel work automatically. A conflict happens only in one specific situation: two people change the same lines of the same file, based on the same starting point, and both try to share their version. Git cannot know which one is "right", so it stops and asks a human to decide.

Let's walk through it concretely with two teammates, Alice and Bob, who each cloned the same hello repository. Both start from the same commit, in which hello.cpp's greeting line reads:

Setup: add your teammate to the repository

Git Branching

Diverging from the main line of development to work without interfering with it.

1 · What is branching?

Branching is not new in Git: almost every version-control system supports it. Branching means diverging from the main line of development and continuing to work without interfering with that main line.

Branches in Git are extremely lightweight. Think of a branch as nothing more than a movable pointer to a specific commit. Because there is no memory overhead, it is cheap and natural to use branches to logically divide your work. Creating one is instant; switching between them just changes which version of the files you see on disk.

Visualize it

As you read, try each action in the interactive branch playground, hosted locally so it works even when the original site is slow or blocked: open Learn Git Branching. Watching the pointers move is the fastest way to build intuition. This tool is the open-source Learn Git Branching by Peter Cottle, used here under the MIT license; all credit goes to the original author.

2 · When do you branch?

So far you have worked on a single branch (master). There are times when you need to temporarily diverge and work on a "separate project". Three common scenarios:

Keep development off the delivered system

You are adding new features to an already delivered system, and you want to make sure your ongoing work does not destabilise the version users depend on until it is ready.

Solution: keep a dev branch separate from master. Merge into master only when the new features are ready to ship.

Hot bug fix

You are mid-way through a new feature when QA reports a critical bug in already-released code that must be fixed immediately.

Solution: switch to master, create a bugfix branch from it, fix the bug, and merge it back into master. Then switch back to your feature branch and carry on, your unfinished work undisturbed.

Work in parallel

Several engineers share one project. The work is split and assigned to individuals who mostly work at the same time. Having everyone commit to one shared branch quickly gets messy.

Solution: each member creates their own task branch off dev. When a task is finished, it merges back into dev.

Notice the pattern

The word merge appears in every scenario. Branches usually represent short-lived work that exists only temporarily. As soon as a branch has served its purpose, merge it back and delete it. Leaving stale branches around (and not merging in time) is a common source of avoidable merge conflicts.

3 · Working with branches

The commands below are all you need day to day. The activities use your hello repository from the Setup Lab.

1) Create a branch: git branch <name>

  • Creates a new branch pointing at the current commit (it does not switch you to it).
  • Does not work if the parent branch is empty (has no commits yet).

cd hello

#   dev
# * master
#   remotes/origin/HEAD -> origin/master
#   remotes/origin/master

Only origin/master shows up under remotes because you have not pushed the new dev branch yet. (More on remote branches below.)

2) Switch to a branch: git checkout <name>

  • Switches to the named branch and updates your workspace files to match it.
  • git switch <name> does exactly the same thing (newer, clearer syntax).
  • git checkout -b <name> creates and switches in one step.
Activity: switch to dev, then create-and-switch to testing 
git checkout dev        # Switched to branch 'dev'
git switch master         # same idea, switch back
git checkout -b testing  # create 'testing' and switch to it at once

3) Delete a branch: git branch -d <name>

  • Deletes the named local branch.
  • You cannot delete the branch you are currently on: switch away first.
  • You cannot delete a branch with unmerged changes (use -D to force, carefully).
Activity: delete the testing branch 
git checkout dev
git branch -d testing    # Deleted branch testing (was dfc0baa).

4) Merge a branch: git merge <name>

Merging brings another branch's work into the current branch. There are two outcomes:

Fast-forward. If master has not moved since you branched, Git just slides the master pointer forward to the tip of dev. No new commit is created.

# commit once on dev, then merge into master
git checkout dev
# create code.txt, then:
git add -A
git commit -m "added code.txt"
git checkout master
git merge dev            # Fast-forward

# before:   c0 - c1 - c2        master -> c1,  dev -> c2
# after:    c0 - c1 - c2        master -> c2,  dev -> c2   (pointer just moved)

Merge commit (three-way merge). If both branches gained commits since they diverged, Git creates a special merge commit with two parents that ties the histories together. This may require resolving a conflict, exactly as in Lab 2.

# commit on master AND on dev, then merge
# on master: modify code.txt, add, commit
git checkout dev
# create resource.txt, add, commit
git checkout master
git merge dev            # creates a merge commit

# before:        c3              master -> c3
#               /
#         c0 - c1 - c2 - c4     dev  -> c4
# after:         c3 ----- c5    c5 = merge commit (parents c3 and c4)
#               /        /
#         c0 - c1 - c2 - c4
Keep the feature branch fresh

After merging dev into master, also update dev so it includes the latest master, which avoids future conflicts: git checkout dev then git merge master.

5) Combine history with rebase: git rebase <name>

Rebasing is another way to combine work. It takes a set of commits, "copies" them, and replays them on top of the checked-out branch, producing a linear history instead of a merge commit.

Rebase rewrites history

Rebasing creates copies of commits; the originals are no longer reachable by their branch. On shared branches this can wipe out other people's work. Do not rebase unless you are 100% sure it is the right tool, and never rebase commits others have already pulled.

The typical local flow: fix a bug on a bugfix branch, rebase it onto master so the fix sits neatly after master's latest commit, resolve any conflict, then fast-forward master and delete the branch. For a deeper comparison see the reference link at the end.

6) Remote branches

So far everything has been local. A name like origin/master is a remote-tracking branch: the convention is <remote name>/<branch name>. It reflects the state of the remote as of your last pull or fetch.

Crucially, remote-tracking branches live in your local repository. Treat them as cached references to the real remote (they are sometimes called "upstreams"). They only update when you communicate with the remote.

7) Publish a new local branch: git push --set-upstream origin <name>

A plain git push only pushes the current branch, and only if it already has a remote counterpart. The first time you push a brand-new local branch, Git does not yet know where to send it:

git checkout dev
git push
# fatal: The current branch dev has no upstream branch.
# To push the current branch and set the remote as upstream, use
#     git push --set-upstream origin dev

The fix is given to you in the message. Running it creates origin/dev and links your local dev to it, so future pushes on dev are just git push:

git push --set-upstream origin dev   # or the short form: git push -u origin dev

8) Pull branches from the remote

When a teammate (or a second clone) has pushed work, you bring it in with git pull on the matching branch. A fresh git clone already captures information about all remote branches.

Activity: sync a change across two clones 
# in a second workspace, Repo2:
git clone git@gitee.com:adasuper/hello.git
git branch -a            # all branch info captured by the clone
# ... in Repo1, change dev, add, commit, push ...
# back in Repo2:
git checkout dev
git pull                 # receive Repo1's latest dev work
A cleaner way to see push and pull

Now that you understand remote branches: git pull is merging the remote branch into your local branch, and git push is merging your local branch into the remote branch.

9) Delete a remote branch: git push -d origin <name>

Deleting a branch locally (git branch -d task) leaves the remote copy in place. To remove it from the remote too:

git push -d origin task   # delete the remote branch origin/task

As always, trim short-lived branches once they have served their purpose to keep the repository tidy.

The Pull Request workflow on Gitee

On a team, you usually do not merge a feature branch yourself. Instead you open a Pull Request so the change can be reviewed first:

  1. Push your feature branch to Gitee (git push -u origin feature/x).
  2. Open a Pull Request (PR) proposing to merge it into master.
  3. A teammate reviews the changes and comments.
  4. Merge the PR, delete the branch, and everyone pulls the updated master.

PRs are where code review happens, and, once we add CI in Module 6, where automated tests gate the merge. PRs can also be linked to issues so that merging automatically closes the task it addressed.

Make

Why manual g++ doesn't scale, and how to describe a build once and repeat it with a single command.

As soon as a project has more than one source file, typing g++ commands by hand becomes error-prone and unrepeatable. Make lets you record your build in one file, the Makefile. You then type make, and it runs the right compiler commands for you, rebuilding only what actually changed.

1 · The simplest Makefile

Recall the hello project from the Setup Lab: a single hello.cpp you compiled by hand with g++ hello.cpp -o hello. A Makefile records that command as a rule. Create a file named Makefile (no extension) next to hello.cpp:

hello: hello.cpp
	g++ hello.cpp -o hello

That single rule has three parts:

  • Target: hello, the file we want to produce (left of the colon).
  • Prerequisites: hello.cpp, what the target is built from (right of the colon).
  • Recipe: the indented g++ … line, the shell command that builds the target.

Now just type make:

make
# g++ hello.cpp -o hello
./hello
# Hello, world!
Tabs, not spaces

Every recipe line must begin with a real Tab character, never spaces; this is Make's most infamous gotcha. If you see Makefile:2: *** missing separator. Stop., your editor turned the Tab into spaces; switch that line's indentation back to a Tab. (In VS Code, the Makefile Tools extension handles this for you.)

2 · The default goal & "up to date"

Running make with no arguments builds the first target in the file, the default goal. You can also name one explicitly: make hello. Run make a second time without changing anything:

make
# make: 'hello' is up to date.

Make compares timestamps: it rebuilds a target only when a prerequisite is newer than the target. Edit hello.cpp (or touch hello.cpp) and make recompiles; otherwise it does nothing. On one file that hardly matters; on a big project it turns a minutes-long rebuild into a seconds-long one. That is the whole point of a build system.

3 · More than one file

Real programs span several files. Let's grow hello by moving the greeting into its own unit, giving three files:

// greeter.h
#ifndef GREETER_H
#define GREETER_H
#include <string>
std::string greet(const std::string& name);
#endif
// greeter.cpp
#include "greeter.h"
std::string greet(const std::string& name) {
    return "Hello, " + name + "!";
}
// main.cpp
#include <iostream>
#include "greeter.h"
int main() {
    std::cout << greet("world") << "\n";
}

The naive Makefile compiles them all in one command:

hello: main.cpp greeter.cpp greeter.h
	g++ main.cpp greeter.cpp -o hello

It works, but it recompiles both sources whenever you touch either one. We can do better.

4 · Separate compilation & incremental builds

Building is really two steps: turn each .cpp into an object file (.o), then link the objects into one executable. Giving each step its own rule lets Make rebuild only what changed:

hello: main.o greeter.o
	g++ main.o greeter.o -o hello

main.o: main.cpp greeter.h
	g++ -c main.cpp

greeter.o: greeter.cpp greeter.h
	g++ -c greeter.cpp

g++ -c main.cpp compiles without linking, producing main.o. Make now understands a small dependency graph:

hello
├── main.o      ← main.cpp + greeter.h
└── greeter.o   ← greeter.cpp + greeter.h

Edit only greeter.cpp and run make: it rebuilds greeter.o and relinks hello, but skips main.o because main.cpp didn't change. Both objects list greeter.h as a prerequisite, so editing the header correctly rebuilds both.

5 · Variables

The compiler name and flags repeat on every line. Pull them into variables and reference them with $(…):

CXX = g++
CXXFLAGS = -std=c++17 -Wall

hello: main.o greeter.o
	$(CXX) $(CXXFLAGS) main.o greeter.o -o hello

main.o: main.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c main.cpp

greeter.o: greeter.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c greeter.cpp

Now adding a flag or switching compilers is a one-line change applied everywhere. CXX and CXXFLAGS are conventional names, but any name works. The two flags we pass are worth knowing:

  • -std=c++17: compile against the C++17 language standard. Without it, g++ may default to an older standard and reject modern syntax; pinning the version makes the build behave the same on every machine.
  • -Wall: turn on the common warnings ("all" the usual ones). Warnings flag suspicious code (an unused variable, a function that forgets to return) that still compiles but is often a bug. Treat them as a free code review.

Other flags you'll meet: -Iinclude (also written -I include) adds a folder to the compiler's header search path, so #include "board.h" is found when the header lives in an include/ subfolder; -g adds debug information; -O2 turns on optimisation.

6 · Automatic variables

The recipes still repeat file names. Make fills in three automatic variables per rule:

  • $@: the target.
  • $^: all prerequisites.
  • $<: the first prerequisite.
hello: main.o greeter.o
	$(CXX) $(CXXFLAGS) $^ -o $@

main.o: main.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $<

greeter.o: greeter.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $<

For hello, $^ expands to main.o greeter.o and $@ to hello. In the object rules we use $< (the .cpp), not $^, so the header isn't handed to the compiler as a source file.

7 · Pattern rules

The two object rules are now identical except for the names. A pattern rule using % as a wildcard collapses them into one rule that builds any .o from the matching .cpp:

%.o: %.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $< -o $@

The % matches the stem: for greeter.o it is greeter, so the prerequisite becomes greeter.cpp. One rule now covers every source file you add.

8 · Phony targets: clean and run

Not every target is a file. clean deletes build output; run builds then launches the program. Since no file named clean exists, make clean normally runs, but if someone ever created a file called clean, Make would think it was "up to date" and skip it. Declaring these targets .PHONY tells Make they are commands, not files:

.PHONY: clean run

clean:
	rm -f hello *.o

run: hello
	./hello

make run depends on hello, so Make builds the program first (if needed), then runs it.

But these two recipes are environment-specific. rm -f and ./hello are Unix conventions (macOS, Linux, and Git Bash). In a native Windows shell (PowerShell or Command Prompt) the delete command is del, and the executable is hello.exe, launched without the ./ prefix. So clean and run have to adapt: the complete Makefile below detects which shell you are running in and picks the right commands automatically.

9 · The complete Makefile

Putting every idea together, and making clean and run work in any shell, gives this complete, portable Makefile for the multi-file hello project:

CXX = g++
CXXFLAGS = -std=c++17 -Wall

# Ask the shell what it is: a POSIX shell (Linux, macOS, Git Bash) has
# `uname`; a native Windows shell (cmd / PowerShell) does not.
UNAME := $(shell uname 2>/dev/null)

ifeq ($(UNAME),)
    EXE = hello.exe
    RM  = del /Q /F
    RUN = $(EXE)
else
    EXE = hello
    RM  = rm -f
    RUN = ./$(EXE)
endif

$(EXE): main.o greeter.o
	$(CXX) $(CXXFLAGS) $^ -o $@

%.o: %.cpp greeter.h
	$(CXX) $(CXXFLAGS) -c $< -o $@

.PHONY: clean run

clean:
	-$(RM) $(EXE) *.o

run: $(EXE)
	$(RUN)

Instead of keying off the operating system, this version asks the shell what it is. The detection line repays reading token by token:

UNAME := $(shell uname 2>/dev/null)
  • UNAME: the variable we are defining (any name works; this one is conventional).
  • :=: a simply-expanded assignment: the right-hand side is evaluated once, right now, and the result is stored. With a plain = the value would be recursively expanded, re-evaluated every time UNAME is used, which would re-run the command on each reference. := runs uname exactly once.
  • $(shell …): Make's shell function: it runs the command inside a subshell and substitutes the command's standard output back into the Makefile (with the trailing newline stripped). So UNAME becomes whatever uname printed.
  • uname: the Unix command that prints the kernel/OS name: Linux, Darwin (macOS), or MINGW64_NT-… (Git Bash). A native Windows shell has no such command.
  • 2>/dev/null: shell redirection: send file descriptor 2 (standard error) to the null device, i.e. discard it. When uname is missing, Windows prints a "command not found" message to stderr; this throws that message away so it doesn't clutter the output, leaving UNAME simply empty.

So UNAME ends up as either the shell's name or an empty string, and two cases follow:

  • Empty (no uname) → Command Prompt or PowerShell: delete with del, run the bare hello.exe.
  • Anything else (a POSIX shell: Linux, Darwin, or Git Bash) → use rm and ./hello.

The rules use $(EXE), $(RM), and $(RUN) instead of hard-coded names, so one file works for everyone. The leading - in -$(RM) … tells Make to ignore errors from that line, so make clean still succeeds even when there is nothing to delete.

Works in any shell

Because the choice is driven by uname rather than the OS, the clean and run targets behave correctly whether you run make from Git Bash, PowerShell, or Command Prompt, with no need to remember which one.

make builds it, make run builds-and-runs, make clean resets. For a deeper reference, the community favourite is makefiletutorial.com.

10 · Organising files into folders

So far every file (headers, sources, the Makefile, and the compiled output) has sat in one folder. That is fine for three files, but it stops scaling the moment a project grows: headers get tangled up with implementation, and, crucially, there is nowhere clean to put tests. The conventional layout separates code by its role:

hello/
├── include/
│   └── greeter.h        # public headers (the interface)
├── src/
│   ├── greeter.cpp      # implementation (the logic)
│   └── main.cpp         # entry point / I/O
├── tests/
│   └── test_greeter.cpp # tests for the logic (added in Module 6)
├── build/               # compiled output: objects + executable (generated; gitignored)
└── Makefile
  • include/ holds the headers: the declarations other files #include.
  • src/ holds the implementation, split so the logic (greeter.cpp) is separate from the entry point / I/O (main.cpp).
  • tests/ holds test programs that exercise the logic.

Why this matters for testing. A test needs to call your logic (greet()) but must not drag in main(): a program can have only one main, and the test supplies its own. Because the logic lives in its own src/greeter.cpp, separate from src/main.cpp, a test in tests/ can compile against greeter.cpp alone, with no keyboard and no clashing main(). In Module 6 you will do exactly that. Organising the files now is what makes automated testing possible later.

Build output should be kept out of the source folders too. This Makefile writes every object file and the executable into a generated build/ folder, so src/, include/, and the project root only ever hold things you actually wrote (add build/ to .gitignore). That takes a few coordinated changes: point the compiler at the headers with -Iinclude, read sources from src/, write outputs under build/, and create that folder before compiling.

CXX = g++
CXXFLAGS = -std=c++17 -Wall -Iinclude
BUILD = build

UNAME := $(shell uname 2>/dev/null)

ifeq ($(UNAME),)
    EXE   = $(BUILD)/hello.exe
    MKDIR = if not exist $(BUILD) mkdir $(BUILD)
    RMDIR = if exist $(BUILD) rmdir /S /Q $(BUILD)
    RUN   = $(subst /,\,$(EXE))
else
    EXE   = $(BUILD)/hello
    MKDIR = mkdir -p $(BUILD)
    RMDIR = rm -rf $(BUILD)
    RUN   = ./$(EXE)
endif

$(EXE): $(BUILD)/main.o $(BUILD)/greeter.o
	$(CXX) $(CXXFLAGS) $^ -o $@

$(BUILD)/%.o: src/%.cpp include/greeter.h | $(BUILD)
	$(CXX) $(CXXFLAGS) -c $< -o $@

$(BUILD):
	$(MKDIR)

.PHONY: clean run

clean:
	$(RMDIR)

run: $(EXE)
	$(RUN)
  • BUILD = build names the output folder once, so every other line refers to it by variable.
  • -Iinclude adds the include/ folder to the compiler's header search path, so #include "greeter.h" resolves even though the header is not beside the source. The name include is only a convention: the flag is -I followed by whatever your folder is called (headers in headers/ would use -Iheaders, with the prerequisite path updated to match). You can list several folders with several -I flags.
  • The pattern rule $(BUILD)/%.o: src/%.cpp reads each source from src/ and writes its object into build/ (so build/greeter.o is built from src/greeter.cpp); include/greeter.h is a prerequisite so editing the header rebuilds the objects.
  • The $(BUILD): rule creates the output folder before anything is compiled into it. Because creating and deleting a folder is shell-specific, the same uname check also sets MKDIR (mkdir -p on Unix vs if not exist … mkdir on Windows) and RMDIR (rm -rf vs rmdir /S /Q). make clean now just removes the whole build/ folder.
  • RUN on Windows wraps the path in $(subst /,\,$(EXE)) because the cmd shell needs back-slashes (build\hello.exe) to launch a program, while g++ and Make accept forward slashes everywhere else.

// src/Board.cpp
#include "Board.h"

Board::Board() {
    cells = {'1','2','3','4','5','6','7','8','9'};
}

bool Board::isValidMove(int cell) const {
    if (cell < 1 || cell > 9) return false;
    char c = cells[cell - 1];
    return c != 'X' && c != 'O';
}

void Board::applyMove(int cell, char player) {
    cells[cell - 1] = player;
}

bool Board::isFull() const {
    for (char c : cells)
        if (c != 'X' && c != 'O') return false;
    return true;
}

char Board::winner() const {
    const int lines[8][3] = {
        {0,1,2}, {3,4,5}, {6,7,8},
        {0,3,6}, {1,4,7}, {2,5,8},
        {0,4,8}, {2,4,6}
    };
    for (auto& l : lines) {
        char a = cells[l[0]];
        if ((a == 'X' || a == 'O') && a == cells[l[1]] && a == cells[l[2]])
            return a;
    }
    return ' ';
}

char Board::cellMark(int cell) const {
    return cells[cell - 1];
}

            return;

Module 6 · Lecture · Class 11

CI/CD Configuration

Automating the build and tests on every change with Gitee Go.

We now connect everything: a build system (Make), tests, and a remote host (Gitee) become an automated pipeline that runs on every push and protects master from broken code.

Testing pure functions

Because Lab 4 separated the game logic into board.cpp, we can test it directly: no keyboard required. A test program calls functions like checkWinner with known inputs and verifies the outputs. Crucially, it signals success or failure through its exit code: 0 means all tests passed, non-zero means something failed. That exit code is what the pipeline watches.

A test target in the Makefile

We add a rule that compiles the test program against board.cpp, and a test rule that runs it:

test_board: tests/test_board.cpp src/board.cpp
	$(CXX) $(CXXFLAGS) -o test_board tests/test_board.cpp src/board.cpp

test: test_board
	./test_board

Then make test builds and runs the tests. Because the test program returns a non-zero exit code on failure, make test itself fails too, which is exactly the signal CI needs.

Gitee Go

Gitee Go is Gitee's built-in CI/CD. You enable it on the repository, and it stores pipeline definitions as YAML files in a .workflow/ folder. A typical pipeline has stages that run on every push:

checkout → install tools → make → make test
  • Each push triggers the pipeline; you watch it run and read the logs.
  • A passing run is green; a failing one is red.
  • Gitee Go provides free build minutes, generous for a class, so every student can run pipelines.
  • A PR pipeline can gate merges: a Pull Request whose tests fail cannot be merged.
This is CD too

Without Docker, "delivery" here means the pipeline produces a verified, runnable build (an artifact) and you tag a release on Gitee: a reliable, automated path from commit to shippable program.

Lab 5: Build & Test Pipeline on Gitee Go

Add unit tests, wire them into a Makefile test target, then automate everything in a pipeline. Watch it go red, then green.

1 · Write a test program

Create tests/test_board.cpp: a tiny, dependency-free harness (no external framework needed, which avoids download problems):

#include "board.h"
#include <iostream>
static int failures = 0;
#define CHECK(c) do{ if(!(c)){ std::cerr<<"FAIL: " #c <<" @"<<__LINE__<<"\n"; ++failures; } }while(0)

int main(){
  Board top{{'X','X','X',' ',' ',' ',' ',' ',' '}};
  CHECK(checkWinner(top)=='X');                 // row win
  Board col{{'O',' ',' ','O',' ',' ','O',' ',' '}};
  CHECK(checkWinner(col)=='O');                 // column win
  Board diag{{'X',' ',' ',' ','X',' ',' ',' ','X'}};
  CHECK(checkWinner(diag)=='X');                // diagonal win
  Board none{{'X','O','X',' ',' ',' ',' ',' ',' '}};
  CHECK(checkWinner(none)==' ');                // no winner
  Board draw{{'X','O','X','X','O','O','O','X','X'}};
  CHECK(isFull(draw) && checkWinner(draw)==' '); // draw
  Board g{{'X',' ',' ',' ',' ',' ',' ',' ',' '}};
  CHECK(!isValidMove(g,0)); CHECK(isValidMove(g,1));

  if(failures==0){ std::cout<<"All tests passed!\n"; return 0; }
  std::cerr<<failures<<" test(s) failed.\n"; return 1;
}

2 · Add a test target to the Makefile

Add these rules to your Makefile (recipe lines start with a Tab), then verify locally with make test:

test_board: tests/test_board.cpp src/board.cpp
	$(CXX) $(CXXFLAGS) -o test_board tests/test_board.cpp src/board.cpp

test: test_board
	./test_board
make test               # builds test_board, then runs it

3 · Create the Gitee Go pipeline

Enable Gitee Go on your repo and add a pipeline. Start from Gitee's shell/build template and set its steps to the commands below (the exact YAML keys come from the template editor: adjust to match the current Gitee Go interface). The pipeline should run the same steps your machine does:

# .workflow/ - illustrative shape; build the real one from Gitee's template
name: build-and-test
trigger: [push, pull_request]
stages:
  - name: build-test
    steps:
      - apt-get install -y make g++      # ensure tools
      - make                          # build the game
      - make test                     # build & run the tests

4 · Make it go red, then green

  1. Push your work and watch the pipeline turn green.
  2. Deliberately break a test (e.g. change an expected winner) and push: watch it turn red and read the failure in the logs.
  3. Fix it and push again → green.
  4. (Optional) Configure the PR pipeline so a Pull Request can't merge while tests fail.

Every push to your repository automatically builds the project and runs the tests on Gitee Go, and you have seen a full red → green cycle.
